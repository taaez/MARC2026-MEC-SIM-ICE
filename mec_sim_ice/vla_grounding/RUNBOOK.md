## 4. 자가 채점

**(a) 결과가 진짜 chungmu 문제셋인지 먼저 검증** — 시나리오 혼선·문항 정의 변경을 잡는다:

```bash
python3 verify_run.py ../../../results/scores.jsonl
```

**(b) 항목별 정확도와 실패 원인 분류:**

```bash
python3 score_report.py ../../../results/scores.jsonl --json report.json
```

출력 내용:
- 항목별 평균 (camera / object_type / landmark / relation / anchor / target)
- 실패 원인 분류 (대상 미탐지 / 카메라 오선택 / 랜드마크 오답 / relation 오답 / 좌표 오차)
- 좌표 오차 분포 — **채점식은 실측 역산 결과 `점수 = 1 - 3D오차/5m`** (허용 반경 5m)
- 카메라 오선택 패턴 (정답 → 제출)
- 문항별 상세 표

**(c) 보존할 실행은 runs/ 로 복사** — 개선 전후 비교용:

```bash
cp ../../../results/scores.jsonl runs/chungmu_$(date +%Y-%m-%d_%H%M).jsonl
```

## 카메라 선택에 대해 알아낸 사실 (2026-08-26, records 39라운드 GT 투영 분석)

기록된 카메라 파라미터로 GT 좌표를 6대에 투영해 확인한 것:

- **CCTV 6대는 서로 다른 공간을 본다 (시야가 겹치지 않는다).** 39문제 중 38개에서
  정답 target 이 보이는 카메라가 **정확히 1대뿐**이다. 즉 카메라 선택은 순위 매기기가
  아니라 "명령이 가리킨 물체 쌍이 실제로 있는 곳 찾기"다.
- **target 클래스만으로는 카메라가 절대 안 정해진다.** 씬에 `umbrella` 4개가 4대에,
  `tumbler` 4개가 3대에, `trash_can` 3개가 3대에 흩어져 있다.
- **랜드마크가 결정적이다.** 39문제 중 18개는 명령이 지목한 랜드마크가 카메라 1대에만
  존재해 그것만으로 확정된다. 나머지 21개 중 20개는 "랜드마크와 target 이 가장 가까운
  카메라" 로 해결된다 → 이론상 상한 38/39 (실제 실행은 15/39 였다).
- **사람 문제의 랜드마크는 0점이지만 65점을 여는 열쇠다.** landmark 배점이 0 이어도
  카메라를 좁혀 주는 단서는 사실상 랜드마크뿐이고, 그게 camera(10)+anchor(15)+target(40)
  을 결정한다. 그래서 배점과 무관하게 선택에 쓴다.

3. ~~랜드마크 판별력 가중~~ — **적용됨(폴백 판단 한정)**. 게이트가 카메라를 1대로 좁혔으면
   그 랜드마크는 변별력이 높다는 뜻이라 카메라를 신뢰한다(`landmark_discriminative`).
   순위 점수식에는 넣지 않았다 — relation 적합도만으로 이미 20/21 이라 상승 여지가 작고
   스케일 튜닝 위험만 커진다.
4. ~~`area_hint` 반영~~ — **적용됨**. 랜드마크 파싱이 실패하는 8문항은 애초에 랜드마크를
   말하지 않고 **구역**만 말한다 ("in the parking lot", "at the park"). 이제
   `AREA_INDICATOR_CLASSES` 로 구역 → 지표 클래스를 매핑해 게이트를 건다
   (`parking` → `CAR_CLASSES`, `park` → `{picnic_table, bench}`). 근거: "주차 구역"
   이라는 말 자체가 "차량이 밀집한 곳" 이라는 뜻이라 **씬이 아니라 단어의 의미에서
   나온 매핑**이다.

   **"있다" 가 아니라 "가장 많다" 로 판정해야 한다** — 처음엔 지표가 하나라도 있으면
   후보로 뒀는데, 실측에서 차량이 6대 중 4대 카메라에 흩어져 잡혀(길가에 세워진 차

### 1. anchor 좌표는 중심점이 아니라 **지면 접촉점**이다

clean 라운드 12개로 `locate()` 의 footprint push 계수와 제출 z 를 스윕한 결과,
anchor 는 `base` z 가 압도적으로 정확했다 (평균 오차 1.00m → 0.64m, 점수
0.800 → 0.872). target(작은 물체)은 반대로 `center` 가 맞아 그대로 뒀다.
자판기·택시처럼 큰 랜드마크에서 center 를 쓰면 **물체 높이의 절반이 그대로 z
오차**가 된다. 채점 GT 의 정의에 관한 사실이라 씬이 바뀌어도 성립한다
(`Located.ground_point`). push 계수는 1.0 이 최적이라 변경 없음.

### 2. 랜드마크 게이트 ∩ 구역 게이트

카메라 오선택 9건 중 **4건이 같은 형태**였다: 명령이 랜드마크와 구역을 **둘 다**
말하는데("... trash can **in the parking lot**") 코드는 랜드마크 게이트가 걸리면
`area_hint` 를 **버렸다**. trash_can 처럼 여러 카메라에 보이는 랜드마크는 그것만으로
안 좁혀지는데, 구역이 그중 하나로 갈라 준다. 두 단서는 독립이므로 이제 **교집합**을
쓴다 (`gate_kind="landmark+area"`). 교집합이 비면 랜드마크 게이트로 되돌아가므로
나빠지는 경로가 없다. 이 4건이 +69.45 / +55.41 / +19.78 / +19.76 로 뒤집혔다.

### 3. 새 배경 안전장치 — `AREA_DOMINANCE_RATIO`

2번은 구역 게이트가 **랜드마크가 있을 때도** 후보를 걸러내게 만들므로, 새 배경에서
구역 지표가 오도하면 정답 카메라를 배제할 수 있는 경로가 새로 생긴다. 그래서
"밀집" 판정에 명시적 기준을 뒀다: **1등이 2등의 2배 이상일 때만** 그 구역으로
인정한다. 근거는 씬이 아니라 말의 의미다 — 차가 4대와 3대로 갈리는 두 곳 중 어느
쪽도 "주차장"이라 단정할 수 없다. 애매하면 게이트가 풀려 이 계층이 없을 때와
같아진다. 이 코퍼스에서는 가드 적용 전후 점수가 **동일**하다(지표가 실제로
압도적이었다) — 지금 비용은 0 이고 새 배경에서만 작동하는 보험이다.
T18(교집합 동작) / T19(애매하면 해제)가 이 성질을 고정한다.

### 4. `DET_CONF` 0.35 → 0.25 (라이브 경로 전용, +4.3)

임계값만 바꿔 39문항을 재채점한 결과다:

| conf | 0.10 | 0.15 | 0.25 | 0.35 |
|---|---|---|---|---|
| Stage1 평균 | 57.80 | 57.80 | 57.80 | **53.48** |

`demo_agents/vla_grounding_agent.py` 가 쓰던 0.35 는 **그 자체로 4.3점을 깎고
있었다**(오프라인 채점은 기본이 0.25 라 위 표의 57.80 에 이미 반영돼 있다).
0.10/0.15/0.25 가 완전히 동일하므로 오검출 여지가 가장 적은 0.25 를 골랐다.

### object_type 이 내려간 이유 (14.23 → 13.46)

카메라가 바뀌면서 사람 문제 2건에서 다른 자세의 사람이 선택돼 situation 이
어긋났다. 그 2건도 camera/anchor/target 을 새로 얻어 총점은 크게 올랐다
(sar01 15.00→34.76, sarH4 15.00→34.78).

## 지금 상한을 막고 있는 것은 로직이 아니라 **탐지 recall** 이다 (2026-08-27 측정)

39라운드 각각에서 **GT 카메라에 GT target 이 실제로 검출되는지**(같은 클래스 탐지가
GT 좌표 2m 이내) 전수 측정했다:

- **GT 카메라에서 target 검출: 23/35** (이미지 없는 4라운드 제외)
- GT 카메라에서 landmark 검출: 29/33

클래스별로 보면 편중이 뚜렷하다 — `tumbler` 5/5 로 멀쩡한데 **`pencilcase` 0/3,
`sunblock` 0/1, `umbrella` 5/11** 이다.

남은 **카메라 오선택 5건은 전부 이 문제**다 (lf06 / lf07 / hf02 / hf06 / rtC2,
모두 GT 가 rig_3_b). 확인한 것:

- GT target 을 6대에 투영하면 **정답 카메라에서 화면 한복판**에 있다
  (예: lf07 rig_3_b px=(947,233)). 즉 "그 카메라에 안 보이는" 것이 아니라 **놓친** 것이다.
- conf 를 0.25 → **0.03 까지 낮춰도 안 나온다** (임계값 문제가 아니다).
- imgsz 를 1280 → **1920 / 2560 으로 올려도 안 나온다** (해상도 문제도 아니다).
- 정답 카메라에는 target 이 아예 없고 다른 카메라에는 그럴듯한 (target, landmark)
  디코이 쌍이 있으므로, **로직으로 구별할 신호 자체가 없다.**

`lf11` / `rt04b` (카메라는 맞지만 target 40점이 0점)도 같은 원인이다: 정답 카메라에서
umbrella 가 안 잡혀 랜드마크(택시)만으로 제출했고, GT 는 택시에서 5.2m 떨어져 있어
`target_coord = anchor_coord` 폴백으로도 못 건진다.

**결론: 다음 실질적 개선은 로직 튜닝이 아니라 `pencilcase` / `sunblock` /
`umbrella` 를 중심으로 한 탐지기 재학습이다.** (작은 물체·원거리 샘플 보강)

## 좌표 변환 로직 검토 결과 (2026-08-27) — 세 가지 막다른 길

좌표(anchor 만점 0/39, target 평균 18.28/40)를 더 밀어보려고 세 방향을 측정했고,
**셋 다 "지금 코드가 이미 맞다"로 끝났다.** 같은 시도를 반복하지 않도록 근거를 남긴다.

### ① footprint push 계수 — 이미 최적 (변경 없음)

`locate()` 는 접촉점→중심 보정을 bbox '가로 폭'에서 얻은 반경만큼 '깊이 방향'으로
민다 (= footprint 정사각형 가정). clean 라운드에서 오차가 전부 같은 부호(카메라
쪽으로 -0.24~-1.66m)라 과소보정을 의심하고 계수를 스윕했다:

| push | 0.6 | 0.8 | **1.0** | 1.2 | 1.4 | 2.0 |
|---|---|---|---|---|---|---|
| Stage1 | 56.75 | 57.46 | **57.80** | 57.91 | 56.51 | 55.63 |

1.2 의 +0.11 은 노이즈이고 1.4 부터는 인스턴스 선택이 뒤집히며 급락한다.
`GroundingConfig.footprint_push` 로 파라미터화만 해 두었다(기본 1.0 = 기존 동작) —
탐지기가 바뀌면 재보정할 수 있게.

### ② 지형고(ground_z) 보정 — 상한이 +1.06 뿐 (도입 안 함)

`get_cctv_ground_height()` 가 주는 값은 **CCTV 폴대 자리의 지면 높이**로 보이고,
그 카메라가 내려다보는 구역의 실제 지형과 최대 0.64m 어긋난다 (rig_3_c: 16.10 vs
실제 ~15.47 — 택시 15.46 / 벤치 15.48 로 서로 다른 두 물체가 일치하니 에셋 pivot
문제가 아니라 지면 자체다). SDK 문서는 "roads and grass differ by a few cm" 라고
적혀 있어 실측과 다르다. 얕은 시야각에서 (수평거리/카메라높이) 배율만큼 증폭돼
최대 2.4m 수평 오차가 된다.

**그런데 지형고를 GT 로 완벽히 안다고 가정해도 39문항 평균은 57.80 → 58.86 (+1.06)
에 그친다.** 채점 허용치가 5m 로 넉넉해서다. 이게 이 방향의 **이론적 상한**이므로
실제 추정치는 더 낮다 → 도입할 가치 없음.

### ③ 클래스별 크기 상수로 지형고 역산 — 원칙 위반 대비 이득 없음 (도입 안 함)

높이 H 를 알면 bbox 상·하단 두 광선으로 그 자리의 지형고가 유일하게 풀린다
(`z_g = C_z + H·B/(A−B)`, A/B = 각 광선의 |수평|/수직 비). 그리고 **크기는 실제로
고정이다** — female_student_01 의 `person_walking` 을 서로 다른 카메라·거리(8.1m /
10.1m / 17.5m)에서 재니 1.59 / 1.64 / 1.70m 로 편차 11cm 였고, `person_walking_away`
도 1.59m 로 일치했다. 자세별로도 일정하다(reaching 2.11 / reclining 1.27 /
lying_down 0.61~0.91 / prone 0.49).

부수적으로 확인된 더 중요한 사실: **올바른 평면 z 를 주면 우리 역투영은 정확하다.**
서 있는 사람의 bbox 하단을 GT z 평면에 역투영했을 때 GT 위치와의 오차가
0.11~0.16m 였다. 즉 좌표 오차는 수식이 아니라 평면 z 하나에서 온다.

그럼에도 도입하지 않는다:
- 상한이 ②의 +1.06 인데, 실제로는 그보다 낮다.
- 작은 물체엔 원리적으로 못 쓴다(두 광선이 거의 평행 → A−B→0 발산). 실측에서도
  떨어뜨려 눕힌 `tumbler` 0.05m / `umbrella` 0.06m 라 사용 불가.
- 랜드마크로 대신 풀 수는 있지만, 측정된 높이가 불안정하다 (클래스당 표본 1~2개,
  `police_car` 0.67m 처럼 명백히 틀린 값 포함).
- 무엇보다 이 파일 상단의 설계 원칙("클래스별 높이·크기 상수를 두지 않는다")을
  깨는 대가로 얻는 게 1점 미만이다.

### 그래서 남은 좌표 손실의 정체는

지형고를 완벽히 고쳐도 anchor 가 0.529(평균 오차 ~2.35m)에 머무는데 **오차 중앙값은
1.32m** 다. 평균이 중앙값보다 훨씬 나쁘다 = 소수의 파국적 케이스가 끌어내리고 있다
= `sar01`/`sarH4` 의 8.37m 처럼 **같은 클래스의 엉뚱한 인스턴스를 고른 경우**다.
즉 남은 좌표 문제는 기하 정밀도가 아니라 **인스턴스 선택**이며, 아래 "중복 인스턴스
오선택" 항목과 같은 뿌리다.

## 남은 개선 후보

- **중복 인스턴스 오선택 — 로직으로 남은 가장 큰 지렛대 (약 +5 예상)**.
  landmark 오답 4건(hf07 / lf08 / lf09 / rt01, 각 35.00점)은 전부 rig_7_a 의
  주차장 문제이고 GT landmark 가 `police_car` 인데 우리는 `normal_car_1` 을 고른다.
  근본 원인은 landmark 가 아니라 **target 인스턴스**를 잘못 고르는 것이다.
  실측(rt01, 같은 카메라 안):

  | 후보 | conf | GT target 과의 거리 |
  |---|---|---|
  | tumbler (진짜) | 0.33 | **0.72m** |
  | police_car (진짜 짝) | 0.58 | 4.54m |
  | tumbler (디코이) | 0.77 | 10.45m |
  | normal_car_1 | 0.96 | 11.97m |

  디코이 tumbler 와 normal_car_1 이 1.9m 로 더 붙어 있어 "가장 가까운 쌍" 이
  진짜 짝(4.54m)을 이긴다. conf 도 디코이가 높아 conf 로도 못 뒤집는다.
  target 인스턴스만 바로잡으면 landmark(10) + anchor(15) + target(40) 이 함께
  살아나 4문항이 각각 35 → 85~90 이 된다.
  주의: 이 문항들의 문구가 "**empty** parking space" 라서 "빈 자리 = 차 옆이
  아니다" 로 읽으면 풀리지만, **근거는 4문항인데 영향 범위는 39문항 전체의 선택
  로직이다.** 본선에서 "empty" 가 다른 맥락으로 쓰이면 멀쩡한 문항이 무너진다 —
  현재 판단은 **도입하지 않음**. (아래 "하드코딩 판별 기준" 의 기준 2 에 걸린다.)

## 하드코딩 판별 기준 (규칙을 추가할지 말지)

대회 요구사항이 "문제·배경이 바뀐다, 씬 하드코딩 금지" 이므로, 규칙 추가 여부는
아래 **두 가지를 모두** 통과할 때만 승인한다.

**기준 1 — 이 씬을 한 번도 안 본 사람이, 공식 asset 로스터와 영어 단어 뜻만 알고도
같은 규칙을 쓸 것인가?**
- 통과: `AREA_INDICATOR_CLASSES`("주차 구역" = 차가 밀집한 곳) — 사전적 의미다.
- 탈락: 클래스별 크기 상수 — 이 씬 데이터에서 역산한 값이라 본선 검증이 불가능하다.

**기준 2 — 근거의 크기가 영향 범위에 비례하는가?**
- 통과: `AREA_DOMINANCE_RATIO = 2.0` — "명확히 압도적일 때만" 이라는 성질을 넣은
  것이고, 이 코퍼스에서 점수 변화가 0 임을 확인했다(비용 없는 보험).
- 탈락: "empty → 먼 쪽 선호" — 근거 4문항 vs 영향 39문항. 비례하지 않는다.
- **명시 랜드마크 파싱 실패 보완**: 위 8문항은 area 게이트로 카메라는 잡지만,
  landmark 필드 자체는 "target 에 가장 가까운 랜드마크" 로 추정한다. object 문제
  4건(lf08/lf09/rt01/rt02)은 landmark 배점 10점이 걸려 있어 여기서 더 딸 여지가 있다.
- **`sar04_table_lie`**: GT target 이 6대 어디에도 투영되지 않는다 (데이터 이상).
  다른 라운드를 다시 수집하기 전엔 이 문항은 상한이 막혀 있다.
