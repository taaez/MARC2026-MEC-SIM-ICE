# 폴백 모델(Grounding DINO / Qwen / pose) 켜고 끄면서 검증하기

**대상**: 팀원 누구나. GPU 있는 머신(연구실 데스크탑 RTX 5060 Ti 8GB, 또는 GPU 있는
개인 PC)에서 Isaac Sim 없이 돌린다.
**왜 나눠서 켜야 하나**: 우리 개발 GPU는 8GB 한 장이고 Isaac Sim과 나눠 써야 한다.
모델을 전부 올리면 OOM이 난다 — 실측으로 이미 두 번 터졌다. 그래서 "뭘 켜고 뭘 끄고"를
조합해가며 재는 것이 이 문서의 목적이다.

> 채점 서버(RTX PRO 5000 48GB)에는 이 제약이 없다. 전부 켜도 여유롭다.
> 8GB는 **우리 개발 환경만의 제약**이다.

---

## 0. 30초 요약

```bash
# 리포 루트에서. 인자 없이도 돌지만, 8GB면 아래처럼 나눠 돌린다.
python3 mec_sim_ice/score.py --no-dino --no-vlm     # ① 기준선 (YOLO+기하만)
MARC_DINO_BATCH=2 \
python3 mec_sim_ice/score.py --dino --no-vlm        # ② 제출 기본 구성
python3 mec_sim_ice/taejeong/validation/probe_vlm.py --run   # ③ Qwen 단독 검증
```

`mec_sim_ice/score.py`는 `taejeong/validation/offline_score.py`를 부르는 20줄짜리
래퍼다. **둘은 완전히 같은 프로그램**이고 옵션도 그대로 통한다. 리포 루트에서
치기 짧아서 `score.py`를 쓸 뿐이다.

## 1. 지금 파이프라인에 붙어 있는 모델 4개

| 모델 | 무엇 | 기본값 | VRAM | 끄는 법 |
|---|---|---|---|---|
| **YOLO11** (`best.pt`) | 주 탐지기. 34클래스 | 항상 ON (끌 수 없음) | ~0.5 GB | — |
| **Grounding DINO** (`grounding-dino-base`, fp32) | YOLO가 놓친 target/landmark를 개방어휘로 재탐색 | **ON** | 가중치 0.95 GB<br>**8타일 forward 피크 6.37 GiB** | `--no-dino` |
| **Qwen2.5-1.5B-Instruct** (bf16, 텍스트 전용) | 파서가 못 푼 문장을 다시 해석 | **OFF** | ~3.1 GB | `--vlm`으로 켬 |
| **YOLO11m-pose** | 사람 target의 발목 가로좌표 보정 | **ON** | ~0.5 GB | `MARC_DISABLE_POSE_KEYPOINTS=1` |

세 폴백 모두 **순수 가산 계층**이다 — 탐지를 추가하거나 파싱 결과를 고칠 뿐,
제출 경로를 따로 만들지 않는다. 그래서 다 꺼도 파이프라인은 그대로 돈다(점수만
낮아진다).

### 로드 실패는 조용하다 (중요)

세 모델 모두 로드에 실패하면 **경고 한 줄만 남기고 그냥 진행한다**. 크래시하지
않는다. 그래서 "켰다고 생각했는데 실은 안 켜져 있었다"가 생기기 쉽다.
**항상 `[모델]` 줄을 눈으로 확인할 것**:

```
[모델] YOLO=on  DINO=on  VLM=off  pose=on
```

`--json`으로 저장한 리포트에도 `final.fallback`에 같은 내용이 남는다. 서로 다른
머신에서 나온 리포트를 비교할 때 이걸 먼저 맞춰보고 시작해야 사과-오렌지 비교를
피한다.

## 2. 스위치 사용법

### 2-1. 모델별 on/off (권장)

```bash
python3 mec_sim_ice/score.py --dino --no-vlm
```

| 플래그 | 뜻 | 같은 환경변수 |
|---|---|---|
| `--dino` / `--no-dino` | Grounding DINO만 켜고 끔 | `MARC_DISABLE_DINO_FALLBACK=1` |
| `--vlm` / `--no-vlm` | Qwen만 켜고 끔 | `MARC_ENABLE_VLM=1` / `MARC_DISABLE_VLM=1` |

플래그는 내부에서 **환경변수로 번역돼서** 적용된다. 판정의 단일 출처는
`dino_fallback.is_disabled()` / `vlm_fallback.is_disabled()`이고, **라이브
에이전트(`taejeong_agent_vla.py`)도 같은 함수를 본다.** 그래서 오프라인에서 켠 조합이
라이브에서 그대로 재현된다 — 이게 별도 분기를 안 만든 이유다.

플래그를 안 주면 셸에서 미리 `export` 한 값이 그대로 산다.

### 2-2. 계층 전체 on/off (기존 스위치)

`--fallback` / `--no-fallback`은 **폴백 계층 전체**를 강제로 켜고 끈다.
기본은 자동이며, 자동 규칙은 "라이브와 같게 맞추되 못 돌릴 환경이면 조용히 빠지지
말고 알린다"이다:

- `transformers` 없음 → 끄고 이유 출력
- 가속기(CUDA/MPS) 없음 → 끄고 이유 출력 (CPU로 올리면 몇십 분씩 걸린다)
- 그 외 → 켬

`--no-fallback`을 쓰면 라이브보다 약한 파이프라인을 채점하게 된다. 점수를
데스크탑 실측과 그대로 비교하면 안 된다.

> `--fallback`/`--no-fallback`(마스터)과 `--dino`/`--vlm`(개별)은 층이 다르다.
> 마스터가 꺼지면 개별 플래그와 무관하게 둘 다 안 올라간다.

### 2-3. pose는 아직 플래그가 없다

pose는 `--fallback`과 무관하게 항상 켠다(라이브가 항상 켜므로 맞춘 것). 끄려면
환경변수를 쓴다:

```bash
MARC_DISABLE_POSE_KEYPOINTS=1 python3 mec_sim_ice/score.py --dino --no-vlm
```

### 2-4. 8GB에서 DINO를 안전하게

```bash
MARC_DINO_BATCH=2 python3 mec_sim_ice/score.py --dino --no-vlm
```

DINO는 whole-frame이 불확실하면 화면을 8분할해 **한 번에 8장을 batch forward**한다.
fp32라 이 forward 하나가 6.37 GiB를 실제로 할당한다(실측, RTX 5060 Ti). 7.53 GiB
카드에서 터진다.

`MARC_DINO_BATCH=2`를 주면 처음부터 2장씩 나눠 넣는다. 안 줘도 OOM이 나면 배치를
절반씩 줄여 스스로 맞추지만, **첫 OOM 비용(수십 초 + 로그 오염)을 아끼려면 미리
주는 게 낫다.**

fp32는 바꾸지 말 것. bf16으로 낮췄다가 `grounding-dino`의 텍스트/비전 결합
레이어에서 dtype 불일치로 즉시 크래시한 이력이 있다(커밋 b9420da로 되돌림).

## 3. 8GB 검증 시나리오

`nvidia-smi`로 여유를 먼저 확인한다. **Isaac Sim이 떠 있으면 5GB쯤 먹으므로 무조건
끄고 시작할 것.**

```bash
nvidia-smi --query-gpu=memory.free --format=csv
```

| # | 명령 | 예상 피크 | 무엇을 보나 |
|---|---|---|---|
| 1 | `score.py --no-dino --no-vlm` | ~1 GB | **기준선.** DINO 없이 몇 점인지 |
| 2 | `MARC_DINO_BATCH=2 score.py --dino --no-vlm` | ~3 GB | **제출 기본 구성.** 1번 대비 DINO가 몇 점 올리나 |
| 3 | `probe_vlm.py --run` | ~3.5 GB | **Qwen 단독.** 판정 품질 / 지연 / VRAM |
| 4 | `score.py --dino --no-vlm` (배치 무제한) | ~7.8 GB → 자동 축소 | 채점 서버 동작 재현 확인 |

**1번과 2번의 차이가 DINO의 실제 기여분**이다. 이전 측정에서는 rig_3_b 3문항을
구제해 +107.3점이었다.

`--dino --vlm`을 같이 켜는 조합은 8GB에서 **하지 말 것**. 스크립트가 경고를 띄운다.
채점 서버 구성을 확인하고 싶으면 48GB 환경에서 하거나, 아래 4장처럼 Qwen만 따로
잰다.

### 시간이 오래 걸린다

DINO를 켜면 라운드당 최대 28초까지 걸린다(작은 물체 문항에서 8분할 + 재귀 줌까지
도는 경우). 39라운드면 수십 분이다. 화면에 `[n/39] s1_xxx`가 찍히므로 멈춘 게
아니다. 10초를 넘긴 라운드는 `느림: 21.4s (yolo ... / dino ...)`로 그 자리에서
알려준다.

프레임 대여 채점(records에 없는 문항을 다른 라운드 프레임으로 채점)이 켜져 있으면
비용이 (문항 × 프레임)으로 늘어난다. 급할 때는 `--no-borrowed-frames`로 끈다.

## 4. Qwen 검증은 `probe_vlm.py`로 (score.py 아님)

**`score.py --vlm`으로 Qwen을 재려고 하면 아무것도 안 나온다.** chungmu 39문항
전부가 파서의 닫힌 동의어 사전 안에서 풀려서, Qwen 호출 조건이 **한 번도 성립하지
않기 때문**이다. 모델만 올라가고 호출은 0회다.

직접 확인할 수 있다:

```bash
python3 mec_sim_ice/taejeong/validation/probe_vlm.py --corpus
# -> chungmu 39문항 중 소형 LM 이 걸리는 문항: 0
```

그래서 **일부러 조건을 성립시키는 명령 15개**를 만들어 뒀다.

```bash
# GPU 없이: 각 명령이 노린 경로를 깨우는지 (파서만 돌림, torch 불필요)
python3 mec_sim_ice/taejeong/validation/probe_vlm.py --list

# GPU: 실제 모델 호출 + 지연 + VRAM
MARC_ENABLE_VLM=1 python3 mec_sim_ice/taejeong/validation/probe_vlm.py --run

# 더 작은 모델로도 되는지 비교
MARC_ENABLE_VLM=1 MARC_VLM_MODEL=Qwen/Qwen2.5-0.5B-Instruct \
  python3 mec_sim_ice/taejeong/validation/probe_vlm.py --run
```

### `--run`이 검사하는 5개 경로

전부 `command_parser`의 닫힌 규칙이 막다른 곳(`None`)에 닿았을 때만 도는 것들이고,
**전부 순수 텍스트 이해**다. 좌표·relation·situation 추론에는 쓰지 않는다(그건 기하와
공식 규칙표가 결정론적으로 처리하며, 그게 더 검증 가능하다는 게 이 프로젝트의 설계
결정이다).

| 경로 | 언제 | 무엇을 묻나 |
|---|---|---|
| `behind` | "left ... behind the X"로 중의적일 때 | 구동사(두고 왔다)인가 공간관계(뒤쪽)인가 |
| `landmark` | 기준물을 못 찾았을 때 | 사전 밖 기준물 → DINO 검색어 |
| `is_person` | 물체어도 사람어도 못 찾았을 때 | 사람 찾는 문제인가 물체 찾는 문제인가 |
| `pose` | 사람인데 자세 표현을 못 잡았을 때 | 6개 코스 버킷 중 어느 것 |
| `target` | 물체명을 못 찾았을 때 | 아는 클래스로 복구 or DINO 검색어 |

### 결과에서 볼 것 세 가지

1. **`FAIL` 건수** — 모델이 JSON 형식을 못 지켜 `None`을 낸 횟수. 이 경우 호출부는
   **아무 에러 없이** 기존 동작을 유지한다. 즉 켜 놓고 아무 일도 안 하는 상태가
   로그로는 안 잡힌다. `--run`이 이걸 세는 이유다.
2. **호출당 지연** — 라이브 예산은 문항당 30초다. 한 문항에서 이 경로가 최대 3번까지
   겹칠 수 있으므로(landmark + is_person/pose + target), **평균 × 3**이 DINO 몫을
   얼마나 깎는지 봐야 한다.
3. **VRAM 피크** — 8GB에서 DINO와 같이 올릴 수 있는지 판단용.

### 결과를 어디에 쓰나

Qwen은 지금 **기본 OFF**다. chungmu에서 얻는 게 없으면서 VRAM만 먹기 때문이다.
본선에서 닫힌 어휘를 벗어난 문항이 나오면 `MARC_ENABLE_VLM=1`로 켜야 하는데,
**그때 처음 돌려보는 건 도박이다.** 이 스크립트로 미리 재 둬서, "켤 만한가"를
숫자로 정해두는 게 목적이다.

참고로 코퍼스를 만들면서 확인된 것 두 가지:

- `thermos` / `parasol` / `vacuum flask`는 파서가 혼자 푼다(부분문자열 매치).
  사전에 정말 없는 단어를 고르는 게 생각보다 어렵다 — 좋은 소식이다.
- `"Someone in a red jacket is waving for help."`가 `is_person=False`로 나온다.
  `someone`은 약한 사람 단어라 자세 단서 없이는 사람 판정이 안 선다. 명백한 사람
  문항을 물체 문항처럼 넘기는 **실제 구멍**이고, `classify_person`이 메우라고 있는
  자리다. 본선에 이런 문장이 나오면 Qwen을 켠 쪽이 유리하다.

## 5. 자주 겪는 문제

**`[fallback] 건너뜀 -- transformers 미설치`**
→ `pip install -r docker/requirements.txt`. 폴백 없는 점수는 라이브와 비교 불가다.

**`[fallback] 건너뜀 -- 가속기 없음`**
→ GPU 없는 노트북이다. 파서/기하 테스트(`test_*.py`)와 `probe_vlm.py --list`,
`--corpus`까지만 가능하다.

**`CUDA out of memory`**
→ `nvidia-smi`로 Isaac Sim이 떠 있는지 확인. 껐는데도 나면 `MARC_DINO_BATCH=2`.

**`[pose-kp] 로드 실패`**
→ `yolo11m-pose.pt`가 리포에 없다(`.gitignore`의 `*.pt`에 걸려 있다). 받아서
`mec_sim_ice/demo_agents/weights/`에 두고 `git add -f` 할 것. 이게 없으면 사람 문항
좌표 보정이 통째로 사라지는데 경고 한 줄만 남는다.

**`가중치를 찾을 수 없습니다: .../best.pt`**
→ 학습 담당에게 받아 같은 폴더에 두거나 `--weights` 경로 지정.

**옵션이 `unrecognized arguments`로 튕김**
→ macOS가 `--`를 em-dash(`—`)로 자동 치환한 것이다. 하이픈 두 개로 다시 입력.

## 6. 결과 공유할 때

```bash
python3 mec_sim_ice/score.py --dino --no-vlm --json report_$(whoami)_$(date +%m%d).json
```

리포트를 공유할 때는 **어떤 조합으로 돌렸는지 반드시 같이** 적는다. `--json`으로
저장하면 `final.fallback`에 자동으로 들어간다:

```json
"fallback": {"used": true, "why": "CUDA 사용 가능 -- 라이브 에이전트와 동일 조건",
             "dino": true, "vlm": false, "pose": true}
```

이게 다르면 점수를 비교할 수 없다. GPU 종류도 같이 적어두면 좋다 — 같은 코드라도
MPS(Mac)와 CUDA에서 소수점이 갈리는 사례가 있었다.
