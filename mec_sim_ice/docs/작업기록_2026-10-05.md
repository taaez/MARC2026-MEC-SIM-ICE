## 3. ablation 스크립트 설계

### 3-1. 기존 코드를 안 건드리는 방법
`stage1_ablation.py` 가 `offline_score` 를 import 한 뒤 아래만 런타임에 바꿔 끼우고
`offline_score.main()` 을 그대로 호출한다. 조합마다 **별도 프로세스**라 패치가 서로 새지 않는다.

| 바꿔 끼우는 대상 | 목적 |
|---|---|
| `offline_score.resolve` | `grounding.resolve` 를 복제한 `resolve_ablation()` 으로 교체 (게이트/순위 스위치 추가) |
| `grounding._support_adjusted` | 'on' 지지면 재투영 끄기 |
| `grounding._build_decision` | 제출 좌표 계산 방식 교체, 'on' 상판 fallback 끄기 |
| `offline_score.on_target_probe_augment` | 'on' 재탐색 끄기 |
| `MARC_DISABLE_POSE_KEYPOINTS=1` | 발목 keypoint 끄기 (기존 스위치 그대로) |
| `offline_score.score_round` / `report` | 라운드별 게이트 정보·좌표 오차를 `<ID>.side.json` 으로 수집 |

**복제본 검증**: G4(=현재 코드 구성)를 돌릴 때 매 호출마다 원본 `grounding.resolve` 결과와
대조한다. 2026-10-05 실측: **264회 중 불일치 0회**, 점수 79.81 (기존 채점과 동일).
`grounding.resolve` 가 나중에 바뀌면 이 숫자가 0 이 아니게 되므로, 그때는 복제본을 다시 맞춰야 한다.

### 3-2. 표 A — 카메라 게이팅 (누적, 좌표는 전부 현재 코드)

카메라 선택은 5단계다 (`grounding.py:869-1017`).

| 단계 | 내용 |
|---|---|
| 랜드마크 게이트 | 명령이 지목한 랜드마크가 검출된 카메라만 남김 |
| 구역 게이트 | "parking lot" 등 구역어가 있으면 그 구역 지표 클래스(차량 등)가 **밀집한** 카메라만 남김 (1등 ≥ 2등 × `AREA_DOMINANCE_RATIO`(2.0)) |
| 교집합 | 둘 다 있으면 교집합, 비면 랜드마크 게이트로 되돌아감 |
| 게이트 해제 | 단서가 없으면 전체 카메라 (순수 폴백) |
| 관계 적합도 순위 | 남은 카메라 중 relation 기하 적합도로 선택. 사물은 버킷 일치 우선, 사람은 근접도 우선 |

| ID | 구성 | 게이트 | 카메라 간 순위 |
|---|---|---|---|
| G0 | No gate, confidence ranking | 없음 | target confidence |
| G1 | + Landmark gate | 랜드마크 | confidence |
| G2 | + Area gate (intersection) | 랜드마크 + 구역 | confidence |
| G3 | + Relation-fit ranking (bucket-first) | 랜드마크 + 구역 | 버킷 우선 (사람도 동일) |
| G4 | + Person proximity exception (full) | 랜드마크 + 구역 | 현재 코드 |

- 카메라 **안**에서 target-anchor 쌍을 고르는 규칙(최근접 인스턴스)은 모든 행에서 같다. 바뀌는 것은 카메라 **사이** 선택뿐이다.
- "빈 자리" 명령 전용 선택(`_open_space_pick`)은 모든 행에 그대로 둔다.
- 열 `GT cam excluded` = 게이트가 걸렸는데 정답 카메라가 후보에서 빠진 라운드 수. **리뷰 R2 의 "never exclude" 문장을 이 숫자로 바꾼다.**

### 3-3. 표 B — 좌표 보정 (누적, 게이팅은 전부 현재 코드)

| ID | 구성 | 제출 좌표 | 'on' 보정 | 'on' 재탐색 | 발목 |
|---|---|---|---|---|---|
| C0 | BBox-center back-projection | bbox 중심 픽셀 → 지지 평면 | off | off | off |
| C1 | Bottom-center contact point | bbox 아랫변 중앙 → 지지 평면 | off | off | off |
| C2 | + Footprint-center push | C1 + footprint 반경만큼 카메라 반대쪽으로 (=`ground_point`) | off | off | off |
| C3 | + 'on' support-plane correction | C2 | **on** | off | off |
| C4 | + 'on' low-conf target probe | C2 | on | **on** | off |
| C5 | + Ankle keypoint (full) | 현재 코드 | on | on | **on** |

- C0~C2 는 **제출 좌표만** 바꾸고 카메라/쌍 선택은 그대로다 (선택 기하는 항상 `locate()` 결과를 씀).
- C3 의 'on' 보정은 재투영 결과가 쌍 선택 적합도에도 들어가므로, 선택이 바뀔 수 있다 (실제 코드 동작 그대로).
- C4 의 재탐색은 좌표 보정이 아니라 **탐지 보강**이다. 논문에서는 별도 행이나 각주로 구분하는 것을 권장.
- 발목 보정은 사람 14문항, 'on' 보정은 'on' 명령 문항에만 영향이 있으므로, 표에 `'on' subset`·`Person` 열을 함께 둔다.

### 3-4. 지표 신뢰도 (논문에 쓸 때 주의)
`offline_score.py` 도입부에 적힌 대로, 과거 라이브 39건 전수 대조 결과:
- **camera / object_type(situation) / landmark / relation / anchor 점수 = 플랫폼 채점식과 100% 일치.** 표 A(카메라 정확도, 배제 건수)는 그대로 믿어도 된다.
- **target 좌표 점수는 근사치.** 플랫폼이 물체 크기/영역까지 보는 것으로 추정된다. 그래서 표 B 는 점수보다 **좌표 오차(m, 중앙값)** 를 주 지표로 쓰는 것이 안전하다. 오차는 공식 GT 좌표와의 3D 거리라 근사가 아니다.
- 총점(Stage1 열)은 target 근사의 영향을 받는다. 논문에는 "offline replay score" 로 명시.

## 5. Isaac Sim 데스크탑에서 다시 돌리기

### 5-1. 왜 다시 돌리나
- 현재 records(33라운드, 08-25 세션)는 7문항이 자기 라운드가 없어 다른 프레임을 빌려 채점한다. 새로 기록하면 39문항 전부 자기 프레임으로 채점된다.
- 같은 세션의 **라이브 점수(플랫폼이 직접 계산)** 를 함께 남겨, 오프라인 G4/C5 값이 라이브와 얼마나 맞는지 논문에 근거로 쓸 수 있다.
- 조합별 **라이브** 실행은 11번 × 39라운드라 마감 전 현실적이지 않다. 라이브 1회 + 기록 1회 + 오프라인 ablation 이 현실적인 절차다.
