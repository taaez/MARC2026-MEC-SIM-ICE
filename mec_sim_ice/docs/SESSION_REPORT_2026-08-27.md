## 0. 배경

기존 `demo/weights/best.pt`(57.80점, `test/runs/detect/train-6`에서 나옴)는 train/val을
**같은 생성 배치에서 무작위 분할**해서 썼음 — val이 일반화를 보장 못 하는 구조적 문제.
오늘 목표: train과 완전히 분리된 val 세트를 새로 만들고, 그걸로 재학습·재평가.

## 1. 고정 val 세트 500씬 생성

`marc2026_demo`(자유배치) 시나리오로 500씬 생성. 두 번 문제를 겪고 해결:

1. **1차 크래시**: GPU VRAM 부족. 36시간째 idle 상태이던 `simulation-platform-platform-1`
   컨테이너가 VRAM 5GB를 이미 점유 중 → 새 `dataset-gen` 컨테이너가 나머지 요청하다가
   `ERROR_OUT_OF_DEVICE_MEMORY`로 크래시. idle 컨테이너 정지 후 재시도로 해결.
2. **자동 재시도 스크립트 버그**: "배치 끊기면 병합 후 재요청"하는 감시 루프를 짰는데,
   씬 폴더가 컨테이너(root)로 생성돼서 일반 계정 `mv`/`rm`이 Permission denied로 실패하는데
   exit status를 체크 안 해서 "성공"으로 오인(로그엔 "200장 병합 완료"라 찍혔지만 실제 0장).
   **교훈: 컨테이너가 만든 파일을 호스트에서 옮길 땐 소유권부터 확인.** 재설계: 씬 번호가
   기존 개수에 이어서 붙는다는 걸 확인했으므로 병합 자체가 불필요했음 — 매 배치 후
   `docker run --rm --entrypoint chown -v ...:/data marc-base:ros2-isaacsim-5.1 -R 1000:1000
   /data/marc2026_demo`(sudo 불필요, 이미 로컬에 있는 이미지 재사용)로 소유권만 고치고
   부족분만 재요청. 214 → 414 → 500으로 3번 만에 완료.

결과 위치: 생성 직후엔 `trainer_output/marc2026_demo`(새 500씬)와 `trainer_output/temp`
(원본 601씬 백업) — 사용자가 직접 `mv`로 제자리 복구함(`marc2026_demo`=원본 601씬 학습
데이터, `marc2026_validation`=새 500씬).

## 2. `test/train_yolo11.py` 코드 변경

- **`convert`에 `--train-scenes`/`--val-scenes` 추가**: 기존 `--scenes`(단일 디렉토리
  무작위 분할)와 별개로, 두 개의 완전히 분리된 dataset-gen 출력을 각각 전량 train/val로
  쓸 수 있게 함. 하위 호환 유지.
- **`oversample` 서브커맨드 추가**: Ultralytics 8.4.126엔 YOLOv5식 `--image-weights`가
  없어서, 특정 클래스가 포함된 train 이미지를 N배로 복제(심링크+라벨 복사)하는 걸
  직접 구현. val은 절대 안 건드림(원본 그대로 심링크). `--factor 4`로 sunblock/tissue/
  disposable_cup 4배 오버샘플 → `dataset_v3_oversample/`.
- **`train`에 `--project`/`--name` 추가**: 실험마다 저장 위치를 명시적으로 분리하기 위함
  (전에 `runs/`가 어디 기준인지 헷갈리던 문제 있었음, §5 참고).

점수엔 안 잡힘.

## 4. sunblock/tissue/disposable_cup 라벨 육안 검증

라벨(bbox 좌표)이 틀렸는지 확인하려고 `dataset_v2`에서 6장 골라 확대(6배)해서 직접 봄.
**결론: 라벨 좌표는 정확함(R03 mislabeling 버그 아님). 대신 물체 자체가 육안으로도 거의
안 보임:**
- sunblock/tissue: 무늬 없는 흰색/회색 덩어리라 손(피부/장갑)이나 아스팔트 배경과
  구분이 거의 안 됨. 한 샘플은 박스 안에 **아무것도 안 보일 정도**.
- disposable_cup: 자전거 바퀴살 안에 가려진 샘플 확인 — 심한 가림(occlusion).

즉 데이터를 더 생성해도 "똑같이 안 보이는 인스턴스"만 늘어날 뿐 근본 해결이 안 될 가능성.
에셋 자체를 바꾸는 건 불가(대회 지급 에셋 그대로 나와야 함), 가림 필터링은 이미 어느 정도
돼 있다고 함 → **모델/학습 쪽 레버로 방향 전환.**

## 5. 진행 중 — 개선 실험 3종 비교 (오버샘플 vs 모델스케일업 vs 둘다)

**개념 정리** (헷갈리기 쉬워서 명시):
- **오버샘플(A)**: 모델 구조·가중치 초기화·씬 데이터(원본 601씬) 전부 베이스라인과 동일.
  바뀌는 건 딱 하나, **학습 중 이미지를 보여주는 빈도**뿐 — sunblock/tissue/disposable_cup이
  담긴 학습 이미지를 심링크로 4배 복제해서(`dataset_v3_oversample/`), 한 epoch 안에
  그 이미지들을 4배 더 자주 보게 만듦. 새로 생성한 픽셀은 1개도 없음.

  **⚠ 방법론적 한계 (결과 해석 시 반드시 감안할 것)**: sunblock/tissue/disposable_cup이
  이미지 레벨에서 희귀할 거라 가정하고 설계했는데, 자유배치가 씬당 물체를 많이 넣다 보니
  실제론 **601장 중 529장(88%)**이 이미 이 셋 중 하나를 포함하고 있었음. 그 결과 A는
  "타겟 클래스만 골라 더 보여주기"라기보다 **"데이터의 88%를 사실상 800에폭급으로,
  나머지 12%만 200에폭으로 학습"**에 가까워졌음 — 즉 A와 베이스라인의 차이가
  "오버샘플링 효과"인지 그냥 "총 학습량(에폭×이미지수)이 3.64배 많아진 효과"인지
  **이 실험만으론 분리가 안 됨**. 대조군(같은 총 학습량을 오버샘플 없이 원본 601장을
  더 많은 에폭(~728)으로 돌린 것)을 추가하면 분리 가능하다는 걸 인지하고 있었으나,
  이미 B/C만으로도 시간이 많이 들어서(§ 아래 소요시간 표) **대조군 없이 그대로 진행하기로
  결정함(2026-08-27 논의)**. 그래서 A의 결과는 "오버샘플링이 통했다"가 아니라
  **"오버샘플링 + 긴 학습을 합친 조합이 통했는지"**로 읽어야 함.
- **yolo11s(B, C)**: 우리가 구조를 수정하는 게 아니라 **Ultralytics가 공식 배포하는
  더 큰 기성 체크포인트로 교체**하는 것 (`yolo11n.pt` → `yolo11s.pt`, 둘 다 COCO
  프리트레인드, 채널 수만 다름). 과거 P2/4 탐지 헤드 추가(우리가 직접 구조를
  수정)는 2026-08-25에 시도했다가 34개 클래스 전부 스톡보다 나빠져서 폐기한 이력이
  있음(`YOLO11_학습_가이드.md` §3-1) — 이번엔 그것과 달리 **커스텀 구조 변경이 아니라서**
  리스크가 낮음.
- 추론 속도 참고: 대회는 문제당 30초 예산인데, 오늘 실측한 yolo11n 추론 속도는 이미지당
  2.4~5.0ms — yolo11s로 바뀌어도(통상 1.5~2배) 여전히 예산에 비해 무시할 수준. latency는
  걱정 안 해도 됨.

**C vs B(같은 모델, 오버샘플 유무)**: all은 B가 근소 우위(-0.004)지만 **타겟 3클래스는 C가

1/34"는 **베이스라인 대비**일 때 얘기고, **B 대비로 다시 보면 21개 하락(합계 -0.238) / 13개
상승(합계 +0.098)**으로 훨씬 폭넓게 재분배됐다 — 단순히 "부작용 거의 없음"이 아니라 **용량을
사람 자세 클래스군에서 걷어 타겟 3개(+pencilcase/umbrella)로 옮긴 트레이드오프**에 가깝다.
하락이 두드러진 쪽: person_walking -0.028, person_walking_away -0.026, person_reaching
-0.019, kick_scooter -0.019. 다만 전부 베이스라인보다는 여전히 높아서(그래서 베이스라인 대비
집계에선 1/34로 보였음), 실사용 관점에서 "손해"라 부르긴 어렵고 "B 대비 우선순위가 재배분됨"
정도로 보는 게 정확하다. A는 yolo11n에서 34클래스 중 9개를 베이스라인보다도 낮게 깎았는데
(더 심각한 악화), 같은 오버샘플을 yolo11s에 얹으면 그 정도까진 안 간다 — **모델 용량이
충분하면 오버샘플링의 트레이드오프 폭이 줄어든다는 뜻으로, D/E(GT샘플링 계열, §8)가
yolo11s에서도 순손실이었던 것과 대조적인 결과**. A+B는 개별 효과의 단순 합이 아니라 진짜
시너지이되, 공짜는 아니다(사람 자세 클래스군이 대가를 일부 치름).

**~~결론 — C가 최종 배포 후보로 가장 유력~~ → 철회. 실제 과제 채점(records)에서 뒤집힘, 아래
§9.2 참고.**

**B 완료 (2026-08-27 18:50, 200 epoch 정상 종료, exit=0). yolo11s로 모델만 키움(오버샘플
없음, confound 없는 순수 실험) — A보다 훨씬 큰 개선폭, 특히 타겟 클래스에 불균형하게 더
크게 작용함:**
- 전체(all) 개선폭: mAP50 +0.051(+6.4%), R +0.054(+7.4%) — A(+1.4%/+2.2%)보다 큼
- sunblock: mAP50 +0.064(+16.4%), R +0.037
- tissue: mAP50 +0.105(+25.4%), R +0.134(+49.6%)
- disposable_cup: mAP50 +0.147(+34.3%), **R +0.211(+75.6%, 가장 큰 개선)**

**A와 달리 B는 confound 문제가 없음** — A는 "all" 개선폭과 타겟 클래스 개선폭이 비슷한
비율이라 "오버샘플링 자체가 타겟팅으로 유효했다"고 단정 못 했는데, B는 "all" 개선폭(+6.4%)
대비 타겟 클래스 개선폭(+16~34%)이 훨씬 크게 불균형함. 즉 모델 용량(채널 폭) 증가가
sunblock/tissue/disposable_cup처럼 원래 어렵던 클래스에 더 크게, 더 confound 없이 작용했다는
증거. C(yolo11s+오버샘플)가 끝나면 오버샘플이 B 대비 추가 이득을 주는지(진짜 독립 효과인지)
확인 가능.

**A 완료 (2026-08-27 17:25, 198 epoch 학습됨 — 마지막 2 epoch은 patience/조기 로그 절단으로
안 보이지만 정상 종료). 타겟 3클래스 전부 개선:**

## 6. 다음 단계 논의 — 데이터 증강 방향 검토

A(오버샘플)도 새 씬을 하나도 안 늘리고 sunblock/tissue/disposable_cup을 개선시켰다는 사실은
"생성량 부족"이라기보다 **"어려운 인스턴스에 대한 유효 학습 노출(gradient exposure) 부족"**
쪽에 더 가까운 증거로 해석. 이 관점에서 효율적 증강 후보를 검토했고, 처음 제안한 4가지 중
둘은 재검토 후 철회함.

**최초 제안 4가지와 검증 결과:**

| # | 아이디어 | 결론 |
|---|---|---|
| 1 | 타일링/SAHI 방식 크롭 학습·추론 | **철회.** "원본 렌더 해상도가 imgsz보다 높을 것"이라는 전제가 틀림 — 실측 결과 `dataset_v2` 학습 이미지·`records/`의 CCTV png 모두 원본이 이미 1280×720이고 `imgsz=1280`도 동일해서, 다운스케일 자체가 없었음. 타일링해봐야 새 정보 없이 업스케일(보간)만 되고, 프레임당 여러 번 추론해야 해서 계산량은 오히려 imgsz를 직접 올리는 것보다 비쌈. (대안으로 "생성 단계에서 렌더 해상도를 올리자"는 안도 검토했으나 이것도 기각 — 아래 별도 항목 참고.) |
| 2 | 오버샘플링을 "포함 여부"가 아니라 "객체 크기/가시성" 기준으로 가중치 | **철회.** train 라벨 324개 sunblock 인스턴스 실측: 평균 bbox 변 길이 8.07px, 최대 25.5px, **40px 넘는 인스턴스 0개**. "크고 쉬운" sunblock이 사실상 존재하지 않음 — 어느 카메라·어느 씬에서 찍혀도 다 작게 나옴(카메라별 스케일 분석에서도 이미 확인됨, §4 인접 내용). 그래서 "작고 가려진 것만 골라 가중치"를 줘봐야 사실상 A와 동일하게 "sunblock 낀 이미지 전부"가 걸리는 것과 같아, A의 confound(오버샘플링 효과 vs 긴 학습 효과 미분리)를 전혀 해소하지 못함. |
| 3 | Copy-paste 증강 (**주의: Ultralytics `copy_paste=` 플래그로는 안 됨 — §7 참고**) | **유지.** 3D LiDAR 탐지 문헌의 GT/database sampling(SECOND, PointPillars 등에서 인스턴스를 다른 씬에 합성해 밀도를 인위적으로 늘리는 기법)과 개념적으로 동일. 자산 형태·재질은 안 건드리고 "등장 빈도·배치 다양성"만 늘리는 방식이라 대회 규정(자산 변형 불가)에도 안 걸릴 것으로 판단. 기존 인스턴스 재가중치(#2)와 달리 실제로 새로운 co-occurrence를 만들어내는 방법이라 남은 후보 중 근거가 가장 탄탄함. |
| 4 | Mosaic 비중 줄이기(특히 초반 에폭) | **철회.** Mosaic은 YOLO 계열에서 원래 작은 객체 탐지를 돕는 용도로 쓰이는 게 정설(YOLOv4 논문 이후 통설 — 4장을 합쳐 다양한 스케일에 노출시키는 게 취지). `close_mosaic=10`으로 막판만 끄는 것도 작은 객체 보호 목적이 아니라 학습 후반에 실제 추론 분포(mosaic 없는 단일 이미지)로 캘리브레이션하기 위함. "작은 걸 더 작게 만들지 말자"는 논리로 표준 설정을 건드리는 제안이었는데, 이는 §5의 P2 detection head(single-stride 계열) 실패 사례와 같은 함정 — 검증 없이 소수 클래스 보호를 이유로 34클래스 전체에 영향을 주는 전역 설정을 바꾸는 것. 근거 부족으로 철회, 손대지 않기로 함.

**추가 검토 — "생성 단계에서 렌더 해상도를 올린다"(#1의 대안): 기각.** 세 가지 이유로 성립
안 함:

1. **실전 CCTV 피드가 1280×720으로 이미 확정됨.** `mec_sim_ice/records/`는 `MARC_RECORD_DIR`로
   **실제 라이브 라운드에서 덤프한 것**인데 png가 전부 1280×720 — 추측이 아니라 실측 확인.
   [`real_agent_vla.py:89`](real_agent_vla.py#L89)의 `DET_IMGSZ = 1280  # CCTV native
   resolution (1280x720)` 주석도 동일.
2. **설령 올릴 수 있어도 오히려 해로움.** 학습을 고해상도로 하고 추론을 1280×720으로 하면
   train/test 분포 불일치 — sunblock이 학습 땐 24px, 실전엔 8px로 보이는 셈이라 지금보다
   나빠질 수 있음. 학습 해상도는 추론 해상도에 맞추는 게 원칙.
3. **애초에 우리가 못 건드림.** `dataset-gen`과 `platform`(라이브 실행)이 **같은 클로즈드소스
   이미지**(`ghcr.io/marc-challenge/marc-platform-content:2026.R03`)를 씀
   (`simulation-platform/docker-compose.yml:65,107`). 카메라 렌더/퍼블리시 로직이 그 이미지
   내부에 있어 우리가 교체할 수 있는 독립 렌더러가 없음.

> **부수 발견(참고용, 원인 미확인)**: `content-image-2026.R03/config.yaml:45`에는
> `camera_defaults.resolution: [3840, 2160]`(HIKVISION DS-2CD2683G2-LIZS2U 8MP 실물 스펙)로
> 적혀 있고 `marc2026_chungmu.yaml`의 카메라 섹션에는 resolution 오버라이드가 없는데, 실제
> 산출물은 1280×720임. 플랫폼이 내부적으로 다운샘플해 퍼블리시하거나 이 config가 실제 동작과
> 안 맞는 참가자용 사본이거나 둘 중 하나로 보이나, 어느 쪽이든 우리가 제어할 수 없는 영역.

**정리된 최종 방향**: 근거가 남는 건 **copy-paste(#3)**, **모델 용량 증가 지속**(§5 B의
연장선, yolo11m 등) 두 가지.

## 7. 실험 D — GT 샘플링 (copy-paste 증강)

### 7.1 왜 필요했나 (오버샘플링으로는 불가능한 것)

train 라벨 실측: 전체 인스턴스 13,470개 중 타겟 3클래스는 **1,011개(7.5%)**뿐이고, 이미지당
타겟은 **최대 3개**(0개 72장 / 1개 172장 / 2개 232장 / 3개 125장).

즉 이미지 단위 복제(§5 A)는 근본적으로 무딘 도구다 — sunblock 하나를 더 보여주려고 나머지
92.5%의 비타겟 인스턴스까지 통째로 4배 복제하는 셈이고, **아무리 복제해도 타겟 비율 7.5%는
그대로다.** A가 34클래스 중 9개를 악화시킨 것도 이 부작용으로 보인다. GT 샘플링은 비타겟을
전혀 늘리지 않고 타겟 밀도만 직접 올린다.

### 7.2 Ultralytics `copy_paste=` 플래그는 우리 데이터에서 no-op (중요)

세션 중 "`args.yaml`에 `copy_paste=0.0`이니 켜기만 하면 된다"고 판단했으나 **틀렸다.** 실제
소스 확인 결과:

```python
# ultralytics/data/augment.py:1924  (CopyPaste.__call__)
if len(labels["instances"].segments) == 0 or self.p == 0:
    return labels
```

**세그멘테이션 마스크가 없으면 그대로 리턴한다.** dataset-gen은 bbox만 내보내는 detection
포맷(`detections[].bbox`, 마스크 없음)이라 `segments`가 항상 비어 있고, `copy_paste=0.5`를
줘도 **에러 없이 조용히 아무 일도 안 일어난다**(켠 줄 알고 넘어가기 딱 좋은 함정). 그래서
오프라인 전처리 스크립트를 새로 작성함: **`mec_sim_ice/test/gt_sample.py`**.

### 7.3 구현 (`gt_sample.py`)

- **도너 뱅크**: 씬 JSON의 `detections[].occlusion`으로 가려진 인스턴스를 배제하고 크롭 수집.
  `occlusion` 값 분포는 `0.0`(완전 가시) 594개 / `-1.0`(미계산 센티널, **sunblock 전량이
  여기 해당**) 324개 / `0<o<=0.3` 30개 / `>0.3` 63개 → 앞 둘만 채택해 **도너 918개** 확보.
- **크기 보정 — 3D 역투영 대신 실측 캘리브레이션**: Isaac Sim의 euler 관례를 잘못 읽으면
  전 박스가 조용히 오염되므로 카메라 외부 파라미터를 아예 안 쓴다. 대신 (카메라 × 클래스)별로
  `객체 크기 = a + b·(이미지 세로 위치)`를 실측 회귀 — **r = +0.79 ~ +0.99**(대부분 0.94 이상)로
  거의 완벽한 선형이라, 붙이는 행 위치만으로 정확한 크기가 나온다. 외부 파라미터 의존 0.
- **배치**: 해당 카메라에서 dataset-gen이 실제로 **작은 물건**(mug/tumbler/sunblock/umbrella/
  pencilcase/cola_can/cracker_box/disposable_cup/tissue/juice 10종)을 놓았던 지면 위치
  풀(3,212개)에서 샘플링(±12px 지터). 기존 박스와 IoU>0.3이거나 자기보다 작은 박스 안에
  중심이 들어가면 거부, 최대 25회 재시도.
- **"설 수 없는 곳" 거부 — 박스가 아니라 지면 접점으로 판정**: 물건이 차 **앞에** 서서 차체를
  가리는 건 물리적으로 정상이므로 박스 겹침으로 거부하면 정상 배치까지 버리게 된다. 대신
  **지면에 닿는 점**이 대상 실루엣 **안**에 들어가면 거부한다(= 몸통/지붕 위에 얹힘). 대상은
  차량 9종 + 자판기·우체통·쓰레기통·소화전 + 사람 9종. `picnic_table`/`bench`는 **일부러
  제외** — 물건을 올려놓는 평평한 면이고 대회 문제 자체가 "테이블 위 머그컵"이다. 판정은 최종
  정수 좌표로 한다(부동소수로 하면 반올림 후 경계에 걸치는 케이스가 남음).
- **알파 마스크(`--blend`, 기본 `auto`)**: 도너 주변 지면색과 다른 픽셀만 남긴다. 시행착오
  이력이 있음 —
  - `ellipse`(기하학적 페더링): **실패.** 5~15px에서 가늘고 각진 객체를 **동그란 blob으로
    뭉갬** — 학습해야 할 형태 자체를 지워버림. 육안 비교로 확인 후 폐기.
  - `hard`(생짜 사각형): 도너와 목적지 지면 밝기가 다르면 **네모난 이음매**가 남음. 모델이
    객체 대신 이음매를 학습할 위험(실전 영상엔 없는 지름길).
  - `auto`(채택): 도너 지면색 기준으로 배경 픽셀을 제거 → 이음매 없이 형태 보존.

### 7.5 알려진 한계 (논문에 명시할 것)

1. **그림자 없음.** 붙인 객체는 지면에 그림자를 드리우지 않는다. copy-paste 계열의 본질적
   한계이며 3D GT 샘플링도 동일한 제약을 안고 쓰인다.
2. **일부가 지면이 아닌 표면에 얹힘.** 표본 40개 육안 검수 결과 3~4개(약 8~10%)가 차체·타이어
   위에 붙었다. 박스가 지면 접점에서 **위로** 뻗기 때문 — 지면 위치 자체는 맞지만 뒤에 차량이
   있으면 박스가 차체를 덮는다. 차 앞에 놓인 컵이 차체를 배경으로 보이는 건 물리적으로
   타당하나 타이어 정중앙에 얹힌 것은 아니다. 개선하려면 배치 후보를 깊이/표면 판정으로
   걸러야 함.
3. **고정 증가량(+3)이며 top-up 방식이 아님.** 3D 문헌의 `db_sampler`는 보통
   `sample_groups: {Car: 15}` 식으로 "목표 개수까지 채우는" top-up을 쓴다. 우리는 "무조건 3개
   추가"라 원본 편차가 보존된다(0→3, 3→6). top-up의 주 이점은 "해당 클래스가 0개인 프레임
   구제"인데, 우리는 이미 88%(529/601)에 타겟이 하나 이상 있어 그 이점이 크지 않다고 판단.

### 7.6 배치 크기 문제 — 8GB VRAM 한계로 batch=16 불가

첫 실행에서 `CUDA out of memory with batch=16` → Ultralytics 자동 강등(16→8→4). `PYTORCH_CUDA_
ALLOC_CONF=expandable_segments:True`로 단편화를 줄여 재시도했으나 **동일하게 실패**.

원인은 GT 샘플링으로 늘어난 인스턴스 밀도다. TaskAlignedAssigner의 메모리는
`batch × (배치 내 최대 객체 수) × anchor 수`에 비례하는데, 이미지당 최대 인스턴스가 33 → 36으로
늘었고 imgsz=1280의 anchor 수가 크다. batch=8에서 피크 4.42G였으므로 batch=16이면 약 8.8G로
8,151MiB 카드를 넘는다. 베이스라인(13,470 인스턴스)이 겨우 들어가던 것이 15,258개가 되면서
넘어간 것.

**batch를 D만 낮추면 베이스라인(16)과의 비교가 깨지므로, 베이스라인을 batch=8로 재실행해 짝을
맞춘다**(`train_baseline_b8`). 참고로 batch 차이의 영향은 생각보다 작다 —
`trainer.py:302-303`에서 `accumulate = round(nbs / batch)`, `nbs=64`이므로:

| batch | accumulate | 유효 옵티마이저 배치 |
|---|---|---|
| 16 | 4 | 64 |
| 8 | 8 | 64 |

weight_decay도 `weight_decay * batch * accumulate / nbs`로 자동 재조정되어 동일하다. 즉 그래디언트
업데이트는 사실상 같고 **실질 차이는 BatchNorm 통계를 8개로 내느냐 16개로 내느냐뿐**이다. 그래도
조건은 맞추는 것이 원칙이라 재실행함.

(imgsz를 낮춰 메모리를 확보하는 선택지는 배제 — 8px 객체를 다루는 과제에서 해상도를 낮추는 것은
과제 자체를 바꾸는 것.)

### 7.7 실험 D 설정

남겨두되, D와 직접 비교하는 수치는 `train_baseline_b8` 쪽을 쓸 것.)

### 7.9 D 결과 — recall은 올랐으나 precision을 그만큼 잃어 순이득 없음

200 epoch 완주(49분). 비교 대상은 §3 베이스라인(batch=16) — batch=8 짝을 재실행하려다
중단함(아래 참고).

| 클래스 | Precision | Recall | mAP50 |
|---|---|---|---|
| sunblock | 0.790 → **0.572** (-0.218) | 0.338 → 0.379 (+0.041) | 0.390 → 0.376 (-0.014) |
| tissue | 0.783 → 0.744 (-0.039) | 0.270 → 0.335 (+0.065) | 0.414 → 0.408 (-0.006) |
| disposable_cup | 0.752 → 0.693 (-0.059) | 0.279 → 0.385 (+0.106) | 0.428 → 0.457 (+0.029) |
| 전체(all) | 0.849 → 0.853 | 0.734 → 0.742 | 0.797 → 0.801 |

34클래스 집계:

| | mAP50 | Recall | Precision |
|---|---|---|---|
| 타겟 3개 | **+0.0030** | **+0.0707** | **-0.1053** |
| 비타겟 31개 | +0.0039 | +0.0019 | +0.0147 |

mAP50이 나빠진 클래스 15개 (A는 9개, B는 0개). 다만 비타겟 평균이 +0.0039로 양수라, A처럼
계통적으로 깎아먹었다기보다 잔변동(churn)이 큰 쪽에 가깝다.

**해석**: 설계 의도(타겟 recall 상승)는 달성했으나 precision을 같은 크기만큼 잃어 **mAP50 순이득이
사실상 0**. 모델의 판별력이 좋아진 것이 아니라 이 클래스들을 더 적극적으로 예측하도록
**동작점(operating point)만 이동**한 것으로 보인다 — 타겟 밀도를 7.5%→18.4%로 올린 만큼 클래스
사전확률이 올라간 결과.

**sunblock의 precision 폭락(-0.218)에 대한 가설**: sunblock은 §7.3에서 확인했듯 **324개 전량이
`occlusion=-1`(미계산 센티널)** 이라 "가려지지 않음"을 검증하지 못한 채 전량 도너로 채택했다.
실제로는 가려진 크롭이 섞여 잘못된 외형을 학습시켰을 가능성이 있다. 세 타겟 중 이 문제가 있는
유일한 클래스가 precision도 압도적으로 크게 떨어진 것은 우연으로 보기 어렵다. (검증하려면
sunblock 도너를 다른 기준 — 예: bbox 종횡비/면적 이상치 제거 — 으로 걸러 재실험 필요.)

> **batch=8 베이스라인 재실행은 취소함.** `trainer.py:302`의 `accumulate = round(nbs/batch)`로
> 유효 옵티마이저 배치가 batch 16/8 모두 64로 동일하고 weight_decay도 자동 재조정되므로, 실질
> 차이는 BatchNorm 통계뿐이라는 판단(§7.6). 따라서 위 비교는 batch가 다른 채로 이루어졌다는
> 점을 한계로 명시해둔다.

## 8. 실험 E = B + D (yolo11s + GT 샘플링)

### 8.1 가설

D의 실패 원인이 **모델 용량 한계**일 가능성. yolo11n(2.6M)에 어려운 클래스 인스턴스를 2.8배로
밀어넣었더니, 제대로 구분할 여력이 없어 "더 자주 쏘는" 쪽으로 대응했다(recall↑ precision↓).
yolo11s는 파라미터가 약 4배이고, §5에서 **P·R을 동시에 올리면서 나빠진 클래스가 0개**였던 유일한
실험이다. 용량이 있으면 D가 만든 recall 여력을 오탐이 아니라 실제 이득으로 전환할 수 있다는 것이
이 실험의 가설.

기대 안 되는 조합(참고): **A+B(=C)** 는 epoch 52에서 0.843, B 최종 0.848로 추가 이득 신호가
없었고, **A+D** 는 둘 다 yolo11n에서 precision을 대가로 recall을 사는 같은 기전이라 약점만 겹친다.

### 8.2 설정

```
weights=yolo11s.pt, data=dataset_v4_gtsample/data.yaml
epochs=200, imgsz=1280, batch=8, workers=8, PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True
--name train_E_s_gtsample
```

batch=8인 이유: 메모리를 지배하는 것은 모델 크기가 아니라 **인스턴스 밀도**임이 확인됨 —
B(yolo11s/v2/b16)는 피크 2.5~2.7G인데 D(yolo11n/v4/b8)는 4.9~6.8G였다. yolo11n+v4가 이미
batch=16에서 OOM이었으므로 더 큰 yolo11s는 불가.

비교 관계:
- **E vs D**: batch·데이터·에폭 동일, **모델만 다름** → 용량 가설의 직접 검정
- **E vs B**: 모델·에폭 동일, 데이터(GT샘플링)와 batch가 다름 → GT샘플링의 순효과(batch 차이 한계 있음)

### 8.3 주의 — 지금까지의 판단 지표(mAP50)가 대회 점수와 다름

실제 파이프라인([`real_agent_vla.py`](real_agent_vla.py#L163-L181))은 `conf=0.35` 고정 임계값에서
해당 클래스 **최고 신뢰도 박스 하나만** 고르고, 랜드마크가 같이 보이는 카메라를 찾는 방식이다.
즉 "임계값 0.35에서 맞는 카메라에 타겟이 잡히는가"가 전부인데, mAP50은 모든 임계값에 걸쳐 적분한
값이라 이것과 다르다. **D처럼 recall↑/precision↓인 모델은 mAP가 제자리여도 실제 과제 점수는 다를
수 있다.**

학습 없이 실제 과제로 채점하는 도구가 이미 있음:

```
python3 mec_sim_ice/tools/run_offline_real_vla.py \
  --records ./mec_sim_ice/records \
  --gt mec_sim_ice/taejeong/content-image-2026.R03/marc2026_chungmu.yaml \
  --weights <각 실험의 best.pt> --conf 0.35
```

기존 가중치 5개(구 best.pt / 베이스라인 / A / B / D)에 E까지 전부 이걸로 채점해 **실제 순위**를
확인할 것. mAP 기준 순위와 다를 수 있다.

### 8.4 E 결과 — 용량 가설은 확인, 그러나 시너지는 없음

200 epoch 완주. 타겟 3클래스 per-class (모두 val 500씬 기준):

| 클래스 | baseline (n,v2,b16) | B (s,v2,b16) | D (n,v4,b8) | **E (s,v4,b4)** |
|---|---|---|---|---|
| | P / R / mAP50 | P / R / mAP50 | P / R / mAP50 | P / R / mAP50 |
| all | 0.849/0.734/0.797 | 0.903/0.788/0.848 | 0.853/0.742/0.801 | 0.893/0.789/0.844 |
| sunblock | 0.790/0.338/0.390 | 0.774/0.375/0.454 | 0.572/0.379/0.376 | 0.701/0.397/0.426 |
| tissue | 0.783/0.270/0.414 | 0.831/0.404/0.519 | 0.744/0.335/0.408 | 0.777/0.452/0.491 |
| disposable_cup | 0.752/0.279/0.428 | 0.822/0.490/0.575 | 0.693/0.385/0.457 | 0.779/0.500/0.560 |

34클래스 집계 (베이스라인 대비):

| 실험 | 타겟 mAP50 | 타겟 R | 타겟 P | 비타겟 mAP50 | 나빠진 클래스 |
|---|---|---|---|---|---|
| A (n + 오버샘플) | +0.0447 | +0.0620 | -0.0103 | +0.0074 | 9/34 |
| **B (s)** | **+0.1053** | +0.1273 | **+0.0340** | +0.0455 | **0/34** |
| D (n + GT샘플링) | +0.0030 | +0.0707 | **-0.1053** | +0.0039 | 15/34 |
| **E (s + GT샘플링)** | +0.0817 | **+0.1540** | -0.0227 | +0.0433 | **0/34** |

**(1) 용량 가설은 확인됨.** GT 샘플링의 precision 손실이 yolo11n에서 **-0.105**였는데 yolo11s에서는
**-0.023**으로 1/5 수준까지 줄었다. 게다가 E는 batch=4로 D(batch=8)보다 **더 불리한** 조건이었으므로,
용량 효과는 오히려 과소평가된 값이다. "D의 precision 붕괴는 yolo11n의 용량 부족 때문"이라는
§8.1 가설은 지지된다.

**(2) 그러나 시너지는 없음 — E는 B를 이기지 못함.** 같은 모델에서 GT 샘플링만 더한 순효과(E vs B):

| 클래스 | P | R | mAP50 |
|---|---|---|---|
| sunblock | -0.073 | +0.022 | **-0.028** |
| tissue | -0.054 | +0.048 | **-0.028** |
| disposable_cup | -0.043 | +0.010 | **-0.015** |
| all | -0.010 | +0.001 | -0.004 |

세 타겟 모두 mAP50이 하락했다. **GT 샘플링은 yolo11s에서도 주는 것(recall)보다 뺏는 것(precision)이
크다.** 단, E의 타겟 recall +0.154는 전 실험 중 최고이며 B(+0.127)를 앞선다.

> **한계 — batch 교란**: E(batch=4)와 B(batch=16)는 batch가 다르므로 E vs B 차이를 GT 샘플링
> 단독 효과로 단정할 수 없다. 다만 **방향은 신뢰할 수 있다** — batch=4는 BN 통계가 불안정해 E에
> 불리하게 작용하므로, "E가 B보다 낮다"는 관측은 GT 샘플링 효과가 없거나 음(-)이라는 결론을
> 뒤집지 못한다. 반대로 용량 가설(D vs E)은 E가 더 불리한 batch였음에도 이겼으므로 더 강하게
> 지지된다.

|---|---|---|---|---|---|---|
| 구 best.pt | 0.780 | 8/33 (24%) | 19/33 | 25/33 | 15/19 | 11/14 |
| 베이스라인 (n) | 0.797 | 8/33 (24%) | 19/33 | 25/33 | 15/19 | 11/14 |
| A (n+오버샘플) | 0.808 | **10/33 (30%)** | 19/33 | 25/33 | 15/19 | 11/14 |
| **B (s)** | **0.848** | **10/33 (30%)** | 19/33 | 25/33 | 15/19 | 11/14 |
| D (n+GT) | 0.801 | 9/33 (27%) | 19/33 | 25/33 | 15/19 | 11/14 |
| E (s+GT) | 0.844 | **10/33 (30%)** | 19/33 | 25/33 | 15/19 | 11/14 |

**핵심 관측 세 가지:**

1. **mAP와 과제 점수의 상관이 끊겨 있다.** mAP를 0.797→0.848(+6.4%)로 올린 B가, mAP +0.011짜리
   A와 **완전히 동일한 10/33**이다. 이 세션의 GPU 약 6시간이 실제 점수로는 **+2라운드**를 샀다.
2. **5개 필드 중 4개는 YOLO가 손도 못 댄다.** `target_type`/`landmark`/`relation`/`situation`은
   `parse_command()`(텍스트 파싱)가 결정하며 6개 모델 전부 수치가 **동일하다**. 탐지기가
   움직이는 것은 `camera` 하나뿐.
3. **camera 실패 23건 분해** (B 기준): 엉뚱하게 `rig_1_a` 선택 **10건**, 어느 카메라에서도 못
   찾음 7건, 기타 오선택 6건(rig_2_b 3 / rig_3_c 2 / rig_2_c 1). 즉 **16/23이 오선택이고 진짜
   탐지 실패는 7건뿐**이다.

### 9.1 근본 원인 — 파이프라인 로직 결함 2건 + 파서 공백 1건

**(a) 탐욕적 first-match + 카메라 간 점수 비교 없음** ([`real_agent_vla.py:163-201`](real_agent_vla.py#L163-L201))
카메라를 순서대로 돌다가 타겟 클래스와 랜드마크 클래스가 **둘 다 보이는 첫 카메라에서 즉시
`return`**한다. 카메라 목록이 알파벳순이라 `rig_1_a`가 항상 먼저 검사되고, 오선택 10건이 전부
rig_1_a인 것이 이 구조적 편향의 직접 증거다.

**(b) 공간 관계를 한 번도 검증하지 않음.** "머그컵이 피크닉 테이블 **위에**"라는 명령인데, 코드는
머그컵 하나와 테이블 하나가 같은 화면에 있기만 하면 통과시킨다. `relation_hint`는 출력 payload에
실려 나갈 뿐 카메라 선택에 쓰이지 않는다. 자유배치 씬에서 여러 카메라에 컵과 테이블이 동시에
잡히는 것은 흔하므로 이것이 오선택의 실질 원인이다.

**(c) person 라운드의 `target_type` 버그 — 단일 라인.** [`real_agent_vla.py:138`](real_agent_vla.py#L138):

```python
target_type = parsed.target_type or ("person" if parsed.is_person else "")
```

`_best_person_box()`가 **자세 클래스(`pose_class`)를 이미 반환**하는데 `resolve_situation()`에만
쓰고 `target_type`에는 넣지 않아, 항상 일반명 `"person"`을 제출한다. GT는
`person_sitting`/`person_lying_down`/`person_prone`/`person_bending`을 요구한다.
**target_type 실패 14건이 전부 person 라운드**다. 예시(sar02):

```
ours: {"target_type": "person",         "landmark": "vending_machine", "situation": "abnormal"}
GT  : {"target_type": "person_sitting",  camera_id: rig_2_c, ...}
결과: camera ✓  landmark ✓  situation ✓  target_type ✗   ← 이 한 필드만 틀림
```

**(d) 파서 어휘 공백** — landmark 실패 8건은 "empty parking space", "parking lot floor" 같은
표현을 랜드마크(police_car / hydrant 등)로 매핑하지 못해 발생.

### 9.2 대안 총정리 (기대이득 ÷ 비용 순)

**Tier 1 — 학습 불필요, 즉시 큰 이득**

| # | 조치 | 기대 이득 | 비용 |
|---|---|---|---|
| 1 | person 라운드에서 `target_type`에 **탐지된 자세 클래스**를 넣기 (이미 보유 중인 `pose_class` 사용) | target_type **19 → 최대 33/33** | 코드 몇 줄 |
| 2 | first-match → **전 카메라 점수 비교 후 최고점 선택**(타겟·랜드마크 신뢰도 결합) | camera 오선택 16건 중 상당수 | 반나절 |
| 3 | **공간 관계 검증**(on/near/beside를 실제 박스 위치로 확인)으로 카메라 후보 필터링 | 2번과 결합 시 camera 정확도 대폭 | 반나절 |
| 4 | 파서 어휘 보강("empty parking space" → police_car 등) | landmark **25 → 최대 33/33** | 1~2시간 |

**Tier 2 — 탐지기 쪽에 남은 것**

| # | 조치 | 판단 |
|---|---|---|
| 5 | **B를 배포 가중치로 채택** | mAP 최고(0.848), 나빠진 클래스 0개, 실제 점수도 최상위 타이. 즉시 실행 |
| 6 | "어느 카메라에서도 못 찾음" **7건** 개별 분석 | 탐지기가 실제로 손해 보는 유일한 지점. 어떤 객체를 놓쳤는지 특정해야 의미 있는 개선 가능 |
| 7 | yolo11m 등 추가 스케일업 | **보류 권장** — B→E에서 mAP 상승이 과제 점수로 옮겨가지 않음이 이미 확인됨 |

**폐기 권고**

- **GT 샘플링(D/E)**: yolo11s에서도 타겟 mAP50 순손실(-0.015~-0.028), 실제 점수도 B와 동률.
  용량 가설(§8.4)은 학술적으로 확인됐으나 실용 가치는 없음.
- **오버샘플링(A)**: B에 지배당하고 9개 클래스 악화. C(A+B)도 epoch 52까지 추가 이득 신호 없었음.
- **P2 / single-stride 계열**: 2026-08-25에 이미 실패(§5).

**요약**: 이 세션의 GPU 약 6시간이 실제 점수로는 +2라운드였다. **Tier 1의 1번(코드 몇 줄)이 그보다
큰 이득을 줄 가능성이 높다.** 탐지기 최적화는 B 채택으로 마무리하고, 이후 작업은 파이프라인
로직과 파서로 옮기는 것이 타당하다.

> **평가 지표 관련 주의**: 이 세션 내내 mAP50으로 판단해왔으나, 대회 파이프라인은 `conf=0.35`
> 고정 임계값에서 클래스별 최고 신뢰도 박스 하나만 쓰므로 지표가 다르다. 앞으로 개선 여부는
> `run_offline_real_vla.py`의 records 채점으로 판단할 것.

### 9.2 C(A+B) 재평가 — mAP 최고였지만 실제 과제 채점에서 B에 뒤짐 (결론 뒤집힘, 2026-08-28)

§5에서 C가 완주된 뒤 "베이스라인 대비 나빠진 클래스 1/34"만 보고 C를 최종 배포 후보로
잠정 결론 냈으나, **B 대비로 다시 보면 21개 클래스가 하락**(person_walking -0.028 등, §5 끝
표 참고)한다는 지적이 있어 §9 방식으로 C를 직접 채점함:

| | camera (33라운드 중) |
|---|---|
| baseline | 8/33 |
| D | 9/33 |
| **C** | **9/33** |
| A | 10/33 |
| **B** | **10/33** |

**C가 D(6개 실험 중 최하위였던 모델)와 같은 급으로 떨어지고, A·B에 못 미친다.** mAP로는 C의
타겟 3클래스가 전 실험 중 최고였는데도 실제 점수는 더 낮다 — §9에서 확인한 "mAP가 과제 점수를
잘 예측 못 한다"가 여기서도 재현됨.

**원인이 특정됨**: B→C 유일하게 뒤바뀐 라운드는 `Find the umbrella on the road next to the
taxi.`(rig_3_c) — B는 umbrella·taxi 둘 다 conf 0.35를 넘겨 카메라를 정확히 골랐는데, C는
taxi(또는 umbrella)가 그 프레임에서 문턱을 못 넘겨 camera_id가 아예 빈 값으로 나왔다. C-B
34클래스 mAP50 표에서 taxi가 -0.009(0.959→0.950)로 밀렸던 게 실제로 이 라운드에서 문턱 미달로
표출된 사례. 오버샘플링이 타겟 3클래스에 쓴 용량을 vehicle류(taxi 포함, normal_car_1/2도
각각 -0.011/-0.013)에서 걷어온 결과로 보인다.

**최종 결론(재확정): C가 아니라 B가 배포 후보.** mAP 타겟 클래스 개선(C)보다 34클래스 전반의
confidence 안정성(B)이 conf=0.35 고정 임계값 파이프라인에서는 더 중요하다는 것을 n=1이지만
구체적 사례로 확인함. 표본이 33라운드/1건 차이라 확정적이진 않지만, mAP·과제점수 두 지표가
같은 방향(B ≥ C)으로 일치하므로 B 쪽으로 판단을 되돌리는 것이 타당.

> **C 관련 메모**: D를 먼저 돌리기 위해 C(yolo11s+오버샘플)를 **epoch 52/200에서 중단**함
> (그 시점 mAP50 0.843, B 최종 0.848과 근접). Ultralytics가 매 에폭 `last.pt`/`best.pt`를
> 갱신하므로 `train_C_both/weights/last.pt`에서 재개 가능 — 학습분 손실 없음.

## ⚠️ 주의 — Stage 1 실행(파이프라인) 관련 내용은 미검증 상태

이 문서의 §9(실제 과제 채점, 병목 분석, Tier 1 대안 목록)를 포함해 **순수 모델(YOLO 학습/성능)
얘기가 아니라 Stage 1 실행 자체(`real_agent_vla.py` 로직, 카메라 선택, target_type 버그 등)를
다루는 내용은 코드가 수정되기 이전 시점 기준**이라 지금 상태와 다를 수 있다. 즉 §9에서 지적한
버그(first-match 카메라 선택, person target_type, 공간관계 미검증 등)가 이후 고쳐졌는지, 혹은
분석 자체가 놓친 부분이 있는지 **전체 코드를 다시 읽고 확인 없이는 부정확할 가능성이 높다.**
Stage 1 실행 관련 결론을 인용하기 전에 반드시 `real_agent_vla.py`(및 관련 파이프라인 코드)
전체를 재확인할 것 — 이 문서에 적힌 코드 인용·라인 번호·버그 설명을 그대로 믿지 말 것.
