## 배경 — 지금까지 결론 요약

- 4개 축(오버샘플 A / 모델스케일 B / GT샘플링 D / B+D=E) 비교 결과 **B(yolo11n→yolo11s, 채널 수만

- GT 샘플링(copy-paste)은 yolo11s에서도 타겟 3클래스 mAP50 순손실(-0.015~-0.028) — 용량을 늘려도

- §9 실제 과제 채점(`run_offline_real_vla.py`, records 33라운드)에서 mAP 상승이 과제 점수로 거의

  본다.

## 오늘 논의 — 모델 이원화 (일반 모델 + 소형 객체 전용 모델)

**아이디어**: yolo11 계열 하나로 34클래스를 전부 처리하는 대신, 두 모델로 쪼갠다.

- **일반 모델**: 31클래스(랜드마크 24 + 이미 잘 잡히는 pickable 7종 — mug/tumbler/umbrella/
  pencilcase/cola_can/cracker_box/juice). sunblock/tissue/disposable_cup은 라벨셋에서 아예 제외.
- **소형 전용 모델**: sunblock/tissue/disposable_cup 3클래스만. 다른 31개 클래스는 존재 자체를
  모름.

**근거**: 이 3클래스 경계는 임의가 아니라 **B 기준 실제 성능 경계와 정확히 일치**한다 — 나머지
31개는 mAP50 0.68~0.94인데 이 셋만 0.45~0.58이다(§5/§8 표 참고). B가 이겼던 이유(채널 증가 →
용량 증가 → 어려운 클래스에 여력)를 한 단계 더 밀면, **아예 공유를 없애서 소형 전용 모델의
전체 용량을 이 3개에만 쓰는 것**이 다음 논리적 스텝.

**한계로 짚어둔 것**: 이 방법의 이득은 순전히 "34클래스와 용량을 안 나눠 쓴다"는 것뿐이고, 원본
렌더가 이미 1280×720이라(§6) 타일링/고해상도로 더 많은 픽셀 정보를 얻는 효과는 없다 — 이 두 개를
혼동하면 안 됨.

**보류한 것**: 파이프라인 개선(Tier 1, §9)과의 우선순위 논쟁이 있었으나, 사용자가 "지금은 모델만
본다"고 범위를 명시적으로 좁혔음. Tier 1 관련 분석·제안은 08-27 문서 §9에 그대로 남겨두고 오늘은
안 건드림.

## §1 아키텍처 상한 확인 — stride 8px가 구조적 해상도 한계

"n/s/m 스케일업이 작은 객체를 더 잘 보게 만드는 거냐"는 질문에서 확인:

```python
YOLO('yolo11n.pt').model.stride  # [8., 16., 32.]
YOLO('yolo11s.pt').model.stride  # [8., 16., 32.]  -- 동일
YOLO('yolo11m.pt').model.stride  # [8., 16., 32.]  -- 동일
```

**n/s/m/l/x 스케일 차이는 채널 폭·깊이(파라미터 수)일 뿐, 격자 해상도(stride)는 전부
동일하다.** imgsz=1280 기준 가장 세밀한 특징맵(stride 8)도 격자 한 칸이 8×8px인데, sunblock/
tissue/disposable_cup 평균 크기가 5~13px로 **그 한 칸과 비슷하거나 더 작다.** COCO의 "small
object" 기준(<32×32px²)보다도 작은 축이라, 어느 스케일을 써도 이 해상도 자체는 못 넘는다.

이 해상도를 넘으려면 구조적으로 stride를 낮춰야 하는데(P2/stride-4 헤드), 그건 2026-08-25에
이미 시도했다가 34클래스 중 다수를 악화시켜 폐기됨(SESSION_REPORT_2026-08-27.md §5 참고).
**즉 현재 YOLO11 계열(표준 3-level FPN) 안에서는 이게 사실상 구조적 천장 — 스케일업(n→s→m)은
이 천장 아래에서 더 잘 짜내는 것이지 천장 자체를 올리는 게 아니다.**

이 한계를 우회하는 방법(모델 이원화 — 일반 모델과 소형 전용 모델 분리)을 논의했으나 위 §0
"다음 할 일"에 적었듯 보류 중.

## §2 소형 객체 전용 모델 — 착수 결정 (2026-08-28 오후)

`small_object_detection_plan.md`(리포 루트, 신규)를 검토하고 설계를 확정했다. §0의 "보류"는
해제됐고, **모델 이원화 + 소형 전용 모델 학습에 착수한다.**

### 2.1 계획서 원안

- 배포 모델 B는 **절대 직접 수정하지 않는다**. 오버샘플·GT copy-paste·P2 head 등 B를 건드린
  시도는 전부 다른 클래스 트레이드오프로 실패했음.
- 대상 3클래스: `disposable_cup` / `sunblock` / `tissue` (bbox 변 길이 평균 5~8px, 최대 40px).
- CIoU → **NWD(Normalized Wasserstein Distance)** 교체/블렌딩. 정규화 상수 C는 논문값 12.8이
  아니라 실측 6~8px로 재튜닝.
- 학습은 원본 이미지, 타일링은 **추론 시점에만**(SAHI).
- 두 모델 결과를 **WBF**로 병합 + 크기 게이팅.
- 검증은 배포 파이프라인의 conf=0.35 컷 적용 후 recall 기준.

### 2.2 로그 실측 재확인 (`test/logs/`)

계획서의 전제를 실제 학습 로그로 검증했다. **전제 성립 확인.**

val 500장 기준 3클래스 인스턴스 수는 희소하지 않다 — disposable_cup 247 / sunblock 219 /
tissue 230. **데이터 부족이 아니라 모델이 못 잡는 것**이다.

B(배포, `train_B_yolo11s`) 클래스별 성적 — 이 3종이 뚜렷한 별도 난이도 계층:

| 클래스 | R | mAP50 | mAP50-95 |
|---|---|---|---|
| disposable_cup | 0.490 | 0.575 | 0.237 |
| sunblock | 0.375 | 0.454 | 0.238 |
| tissue | 0.404 | 0.519 | 0.216 |
| (참고) tumbler | 0.647 | 0.762 | 0.429 |
| (참고) umbrella | 0.674 | 0.782 | 0.471 |
| (참고) pencilcase | 0.725 | 0.811 | 0.491 |
| **모델 평균** | **0.788** | **0.848** | **0.692** |

데이터 개입 실험 전체 비교 (mAP50) — **n→s 스케일업 외에는 아무것도 안 움직인다**:

| mAP50 | baseline-n | A n+오버샘플 | **B s (배포)** | C s+오버샘플 | D n+gt | E s+gt |
|---|---|---|---|---|---|---|
| disposable_cup | 0.428 | 0.477 | **0.575** | 0.598 | 0.457 | 0.560 |
| sunblock | 0.390 | 0.430 | **0.454** | 0.466 | 0.376 | 0.426 |
| tissue | 0.414 | 0.459 | **0.519** | 0.537 | 0.408 | 0.491 |

유의미한 상승은 n→s 단 한 번(+0.10~0.15). s 위에 얹은 오버샘플·GT샘플은 전부 ±0.02 노이즈
범위. **"yolo11s + 데이터 튜닝으로는 이 3종에 대해 한계"라는 판단이 로그로 실증됨.**

기타 로그에서 확인된 제약:
- GPU: RTX 5060 Ti 7.7GB. B 학습 시 imgsz=1280에서 batch 16→8→4 자동 강등 발생.
- train 601장 / val 500장, **background(빈 라벨) 이미지 0장** — false positive 억제에 불리.
- 2모델 추론(B@1280 + SAHI 타일)의 런타임 예산은 아직 미측정.

### 2.3 원안에서 조정한 4가지 (확정 설계)

1. **소형 모델은 격자 타일로 학습한다** (원안: 원본 1280 학습).
   원본 1280 학습 + 640 타일 추론은 학습/추론 스케일이 어긋난다(객체가 6px로 학습됐다가
   추론 땐 12~24px로 보임). SAHI 원 논문도 sliced fine-tuning을 권한다.
   **08-27에 실패한 "GT 크롭 학습"과는 다른 방법**임에 유의 — GT 중심 크롭은 모든 객체를
   화면 중앙에 놓아 객체 위치 분포와 문맥을 파괴하지만, 규칙적 격자 타일은 실제 렌더의
   일부를 자른 것이라 그림자·접지·원근·광원이 전부 보존되고, **빈 타일에서 지금 없는
   background 네거티브까지 생긴다.**
2. **NWD는 1차에서 제외하고, 필요할 때만 추가한다** (원안: 처음부터 NWD).
   타일링으로 객체가 12~24px가 되면 IoU 불안정 문제 자체가 상당 부분 사라진다. NWD +
   추론 타일링을 동시에 넣는 건 과설계 가능성. 진행 순서:
   - **안 B(1차)**: 소형 모델을 타일로 학습(표준 CIoU) + SAHI 추론
   - **안 C(2차, 1차가 부족하면)**: 여기에 NWD 블렌딩 추가 (`loss.py` BboxLoss,
     `tal.py` TaskAlignedAssigner). C는 실측 6~8px 기준 재튜닝
   - NWD는 "원본 학습을 고집할 때"만 정당화된다.
3. **병합은 클래스별 라우팅부터, WBF는 3클래스 내부로 한정** (원안: 전면 WBF).
   두 모델은 담당 클래스가 겹치지 않는다(B 31종 / 소형 3종).
   - 1단계: **클래스별 라우팅** — 31클래스는 B만, 3클래스는 소형 모델만. 클래스마다 한
     모델만 말하므로 **두 모델 confidence 정합이 불필요**하고, WBF가 confidence를 0.35
     밑으로 떨어뜨리는 위험도 원천 소멸.
   - 2단계(필요시): 3클래스 안에서만 WBF. B도 그 3종을 R≈0.4는 맞히므로 합의 시 부스트.
     이때만 calibration 필요.
   - **크기 게이팅은 유지** — 소형 모델이 큰 물체 조각을 오인하는 FP 필터, 저비용.
4. **소형 모델은 전용 conf threshold를 따로 튜닝한다.**
   3클래스·초소형만 본 모델은 calibration이 깨져 있을 것이므로 배포의 conf=0.35를 그대로
   쓰면 안 된다. val의 크기버킷별 recall로 별도 결정.

### 2.4 평가 기준

- val 500장은 분포가 train과 같으므로 **전체 mAP로는 신호가 안 잡힌다.** 실패 모드가
  "원거리 초소형"(rig_2_b/c 5.04m 벽설치, 화면 상단 원경)에 집중돼 있으므로
  **크기 하위 버킷별 recall**로 쪼개서 봐야 한다. val 세트 자체를 다시 만들 필요는 없음.
- 최종 판정은 배포 파이프라인의 **conf=0.35 컷 적용 후** 3클래스 recall.
- 31클래스는 B 그대로이므로 회귀가 원리적으로 불가능하나, 라우팅 구현 버그 확인 차원의
  스모크 테스트는 필요.

### 2.5 정정 사항 (기록용)

- 계획서 §1.2의 "C가 conf=0.35 threshold 문제로 실채점에서 B에 밀렸다"는 기록은 **오기록**.
  C는 mAP 자체가 B보다 낮았다. 이 사례를 근거로 인용하지 말 것. 다만 "오프라인 mAP 개선이
  실채점으로 그대로 이어지지 않는다"는 원칙은 유효하므로 검증 절차에는 유지.
- `YOLO_데이터셋_전략.md`(08-27)의 "구조가 아니라 데이터로 접근한다"는 결론은 **공유 34클래스
  모델**에 대한 것이다. B와 격리된 별도 모델에 NWD/타일링을 쓰는 건 그 제약에 걸리지 않는다.
- `YOLO_데이터셋_전략.md`의 sunblock 0/1, pencilcase 0/3은 **val이 아니라 39개 대회 예제
  라운드** 기준 수치다. val에는 sunblock 인스턴스가 219개 있다.

## §3 구현 — `test/make_tiled_dataset.py` (작성 완료, 실데이터 미실행)

### 3.1 범위 축소 — 일반 모델용 31클래스 데이터셋은 불필요

§0에서 계획했던 `split_by_class.py`의 **"일반 31클래스" 절반은 만들지 않는다.** §2.3-3의
클래스 라우팅으로 가면 일반 모델은 **34클래스 B를 그대로 쓰고 3클래스 출력만 무시**하면
된다. 31클래스로 재학습하는 것은 "B는 절대 수정하지 않는다"는 전제와 충돌하고, 회귀 위험과
학습 비용만 추가된다. 필요한 건 **소형 3클래스 타일 데이터셋 하나**뿐이다.

### 3.2 핵심 발견 — 타일링의 이득은 오직 업스케일 배율에서 나온다

계획서가 명시하지 않은 부분인데, 구현하면서 이게 설계의 중심임이 드러났다.

```
모델이 실제로 보는 객체 크기 = 원본 px × (train_imgsz / tile)
```

- 640 타일을 **imgsz=640으로 학습하면 아무 효과가 없다.** 6px 객체는 여전히 6px이고,
  stride-8 격자 한 칸(8px)에 통째로 들어간다 — 자르기 전과 동일한 문제.
- 640 타일 @ **imgsz=1280** → 2.0배. 6px → 12px, 격자 약 1.9칸.
- 320 타일 @ **imgsz=1280** → 4.0배. 6px → 24px, 격자 약 3.7칸. IoU가 안정화되는 지점.
  대신 타일 수가 이미지당 6개 → 15개로 늘어난다.

**즉 튜닝할 실질 파라미터는 "타일 크기"가 아니라 "배율"이다.** 스크립트가 실행 시마다
달성 배율과 결과 박스 크기 분포(원본 px / 모델 px / 격자 칸 수)를 출력하도록 만들어서,
이 값을 가정이 아니라 확인하고 넘어가게 했다.

### 3.3 스크립트 사양

```
python3 make_tiled_dataset.py --base dataset_v2 --out dataset_v6_small_tiles \
    --classes sunblock,tissue,disposable_cup --tile 640 --train-imgsz 1280
```

- 기존 `dataset_v2`(34클래스, 1280×720)에서 **대상 3클래스만 남기고 0..2로 재인덱싱**
- 겹치는 **규칙적 격자**로 슬라이스(`--overlap` 기본 0.25). 마지막 타일 원점은
  `total - tile`로 스냅 → 패딩 없이 항상 정확히 tile 크기
- 타일 경계에 걸린 박스: 면적의 `--min-vis`(기본 0.5) 이상 남아야 채택. 겹침이 있어
  잘린 조각은 대개 옆 타일에 온전히 들어간다. 객체가 640 타일 대비 5~8px이라 실제로
  거의 발생하지 않으며, 발생 건수를 출력함
- `--min-box`(기본 2px)로 degenerate 슬라이버 제거
- **빈 타일을 background 네거티브로 일부 유지** (`--neg-per-pos`, 기본 0.5).
  원본 데이터셋은 background 이미지가 0장이라 FP 억제에 불리했던 문제를 여기서 보완.
  전량 유지하면 희소 클래스 특성상 압도적으로 빈 타일이라 샘플링함
- 이미지는 실제 크롭 저장(심링크 불가 — 픽셀이 실제로 다름). 소스 이미지당 한 번만
  디코딩하도록 경로 기준 정렬 후 처리

**08-27에 실패한 "GT 크롭 학습"과 다른 점**을 스크립트 docstring에 명시했다: GT 크롭은
모든 객체를 화면 중앙에 놓아 위치 prior와 문맥을 파괴하지만, 규칙적 격자는 원본 렌더를
그대로 자른 것이라 그림자·접지·원근·광원이 보존되고 객체는 있던 자리에 있는다.

### 3.4 검증 상태

합성 데이터(1280×720, 5~8px 타겟 + 200px 디코이 + 타일 경계 걸침 박스)로 스모크 테스트
통과:

- 이미지당 6타일(640) / 15타일(320), 전부 정확히 tile×tile
- 대상 외 클래스(디코이) 전량 제외, 출력 클래스 id 0/1/2만 존재
- 경계 박스 클리핑·min_vis 동작 확인
- 네거티브 샘플링 비율 동작 확인
- 배율 리포트: 640→2.00배(격자 1.86칸), 320→4.00배(격자 3.72칸)

**실데이터(`dataset_v2`) 미실행** — 데이터셋이 Isaac Sim 데스크탑에만 있음.

## §4 구현 완료 — `test/small_object_detection/` 전체 파이프라인

서브모델 관련 코드를 전부 `test/small_object_detection/`으로 모았다. 6개 파일.

| 파일 | 역할 |
|---|---|
| `common.py` | 타일 격자·박스 연산(IoU/NMS/WBF)·`TilingConfig`. **격자 계산의 유일한 정의** |
| `make_tiled_dataset.py` | 1단계. `dataset_v2` → 3클래스 타일 데이터셋 + `tiling.json` |
| `train_small.py` | 2단계. 스톡 yolo11s 학습 (무수정), 배율 검증, 로그 tee |
| `predict.py` | 3단계. `TiledPredictor`(타일 추론·좌표복원·병합) / `RoutedDetector`(B와 라우팅) |
| `evaluate.py` | 4단계. 원본 이미지에서 B단독 vs 라우팅, 크기버킷 recall, conf 스윕 |
| `selftest.py` | 가중치·데이터 없이 도는 자체 점검 33항목 |
| `소형객체_서브모델_가이드.md` | 실행 가이드 (§4.4) |

### 4.1 설계상 중요한 구현 결정

- **`tiling.json`으로 학습/추론 격자 강제 일치.** 타일 크기·겹침·train_imgsz를 데이터셋 옆에
  기록하고, 학습과 추론이 이 파일을 읽는다. 손으로 숫자를 다시 넘기는 경로를 아예 막았다 —
  추론 슬라이싱이 학습과 다르면 **조용히 성능만 떨어지고 에러는 안 난다.**
- **배율 ≤ 1.0이면 학습 거부.** 640 타일을 imgsz 640으로 돌리면 타일링이 아무 효과가 없는데
  겉보기엔 정상 학습으로 보인다. 이걸 실행 시점에 막는다.
- **내부 타일 경계 예측 배제**(SAHI 논문에 없는 추가). 타일 경계에 걸린 객체는 잘린 사본이
  온전한 사본보다 높은 confidence를 받을 수 있어서, NMS만으로는 잘린 쪽이 살아남는다.
  이미지 테두리가 아닌 경계에 붙은 예측은 버린다 — 겹침이 있어 옆 타일이 커버한다.
- **크기 게이팅**(기본 64px) + **서브모델 전용 conf**.
- **`full_pass` 기본 OFF.** SAHI 논문은 전체 이미지 패스를 병합하지만, 이 서브모델은 확대된
  타일만 학습해서 축소된 전체 프레임이 OOD다.

### 4.2 selftest로 실측 확인된 것

33항목 전부 통과. 그 중 설계 근거를 수치로 못박은 두 가지:

```
PASS  2px shift on a 6px box FAILS IoU@0.5
PASS  2px shift on a 6px box PASSES center match
PASS  lone WBF score is halved with 2 models   (0.8 -> 0.4)
```

- **6px 박스는 2px만 밀려도 IoU@0.5를 못 넘는다.** 눈으로는 맞는 탐지인데 학습 신호·평가
  양쪽에서 실패 처리된다는 §1 주장의 실측 근거. `evaluate.py`에 center 매칭을 넣은 이유.
- **WBF는 한 모델만 본 박스의 점수를 절반으로 깎는다.** conf=0.35 컷 아래로 떨어뜨리는
  §2.3-3의 위험이 가설이 아니라 사실임을 확인. 융합을 opt-in으로 둔 근거.

그 외 검증: 타일 격자가 1280×720을 빈틈없이 덮음(640/320 둘 다), 타일 local→global 좌표
변환, 경계 배제(내부는 버리고 이미지 테두리는 유지), 크기 게이팅, 타일 간 중복 병합에서
높은 confidence 사본 생존, 매칭 1:1 보장, AP 계산, 라벨 round-trip.

`make_tiled_dataset` → `train_small`(1 epoch) → `predict`까지 실제 실행 통과. 지표는 전부
0인데 정상 — 합성 단색 이미지라 잡을 게 없다. 확인한 건 배관이지 성능이 아니다.

`small_object_detection/소형객체_서브모델_가이드.md` 작성. 실행 순서(자체점검 → 타일링 →
학습 → 평가 → 배포추론)를 복붙 가능하게 정리하고, **§2에 "기존 모델·논문 대비 차이"** 를

- **WBF 논문 대비**: 기본 미사용(클래스 라우팅), 조건부로 3클래스 내부만

같은 이유로 `test/YOLO11_학습_가이드.md`에도 **§0-0 "스톡 YOLO11 대비 무엇이 다른가"** 를
추가했다(원래 없었음). 요지: B는 "스톡 yolo11s를 imgsz 1280으로 34클래스 파인튜닝"이 전부이고,
P2 헤드·오버샘플·GT샘플·loss 교체는 전부 의도적으로 안 한 것이다.

### 4.5 병합 방식 확정 — 클래스 라우팅(concat), WBF는 옵션 유지

논의 결과 §2.3-3을 더 단순하게 확정했다.

- 대회 추론 시 B와 서브모델이 **같은 프레임**을 본다. 서브모델 타일 결과를 원본 좌표로
  되돌리므로 둘 다 같은 좌표계, 클래스도 disjoint(B 31 / 서브모델 3). → **concat이 구조적으로
  맞는 방식**이지 편법이 아니다. 조율할 지표가 필요한 클래스 충돌이 없다.
- WBF(`--fuse`)는 **지우지 않고 옵션으로 남긴다.** 코드가 격리돼 있고 나중에 비교할 수 있음.
- 남는 실제 리스크: 서브모델 FP가 B의 다른 클래스 박스와 공간 겹침. B는 객체 전체를,
  서브모델 FP는 조각을 잡으므로 높은 IoU 겹침은 드물 것으로 예상되나 미검증.
- `evaluate.py`에 **5번째 리포트 `SUB-MODEL vs B SPATIAL OVERLAP`** 추가:
  서브모델 박스 중 B 박스와 겹치는 비율을 TP/FP로 분해하고 어떤 B 클래스와 겹치는지 집계.
  FP가 confident B 박스에 많이 겹치면 → 단방향 veto가 싸게 걸러줌. TP가 많이 겹치면
  (picnic_table bbox 안의 컵) → veto가 정상 탐지를 죽임, concat 유지. **veto 도입 여부를
  가정이 아니라 이 숫자로 판단.** 로직은 `classify_small_box()`로 분리해 selftest 6항목 추가.
- selftest 총 **39항목** 통과.

### 4.6 부수 발견 — `.gitignore`에 `*.pt` 규칙이 없었다

`.gitignore` 15~17행 주석은 "가중치는 크고 재생성 가능하니 절대 커밋 금지"라고 적어놨는데,
실제 규칙은 `test/runs/` 같은 **디렉토리만** 막고 있었다. Ultralytics는 사전학습 가중치를
**CWD에 다운로드**하므로 `test/`나 `test/small_object_detection/`에 떨어지고, 이 경로들은
어느 규칙에도 안 걸린다 → `git add -A` 한 번이면 18MB 바이너리가 커밋된다.

`*.pt` + `!demo/weights/best.pt` 규칙과 타일 데이터셋 제외 규칙을 추가했다. 기존 커밋에
`.pt`가 섞여 들어간 것은 없음을 확인했다(`git ls-files`에 `.pt` 0건).

> 참고: `YOLO_데이터셋_전략.md` §4의 "`.gitignore`가 `*.pt`를 제외한다"는 서술은 **사실이
> 아니었다.** 이제는 맞는 서술이 됐다.
