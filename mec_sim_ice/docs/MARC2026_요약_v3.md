### 0-2. 설치 순서 (Quickstart, 목표 30분이지만 최초 빌드는 수십 분~수 시간 소요)

```
1) git clone https://github.com/marc-challenge/marc-starter-kit.git
2) NGC 로그인 (최초 1회, 참가자 본인이 직접 — marc.sh setup이 대신 안 해줌)
   docker login nvcr.io
   # Username: $oauthtoken
   # Password: <NGC API Key>
3) base 이미지 빌드 (최초 1회, 시간 오래 걸림 — 진행 없어 보여도 정상)
   bash simulation-platform/marc.sh setup
4) 플랫폼 실행할 시나리오 지정 (.env)
   cd simulation-platform && cp .env.example .env
   # ENV_MARC_SCENARIO=marc2026_demo (기본값) 또는 marc2026_chungmu (전체 자체채점용)
5) 플랫폼 실행
   xhost +local:root   # GUI 모드일 때 최초 1회 (HEADLESS=false가 기본값)
   bash marc.sh platform
   # 최초 실행은 씬 로딩에 2~5분+ 소요, "Isaac Sim is not responding" 경고 떠도 강제종료 금지

6) 데모 실행 (베이스라인 코드 동작 확인)
   export MARC_TEAM_ID=u1
   export MARC_TOKEN=<team-token>
   cd demo && docker compose up
```

- **NGC 로그인은 한 번만 하면 계속 유지**되며, 이후 `marc.sh setup`이 base 이미지 빌드를 대신 처리.
- 플랫폼과 참가자 프로그램은 **한 대의 컴퓨터에서 같이 실행해도 개발 단계에선 무방**함(공식 채점만 서로 다른 컴퓨터+LAN 연결).
- **정정(v3)**: `.env.example`의 `ENV_MARC_SCENARIO` 기본값은 `marc2026_demo`다. 자체 채점까지 하려면 `marc2026_chungmu`로 직접 바꿔야 함.

## 1. 대회 구조 개요

- 로봇: 4륜 섀시 + 6축 로봇팔(Robotiq 2F-140 그리퍼, Kinova Gen3 기반)
- **Stage 1**: CCTV 영상 기반 VLA grounding — 자연어 명령을 듣고 대상 물체/사람의 좌표를 추정해 제출 (로봇 이동 없음, 순수 인식 문제)
- **Stage 2**: grounding + 실제 로봇 주행 + 물건 집기(pick) + 지정 장소로 배달(place)
  - Stage 1과 Stage 2는 **독립된 별개 단계**임. Stage 1의 카메라 선택 결과가 Stage 2로 넘어가는 게 아님.
  - Stage 2의 이동 목표는 grounding이 아니라 `on_stage2_reveal`이 주는 `hint_center`(대략 위치)에서 나옴 — grounding이 틀려도 수거는 계속 진행 가능.
- 통신: 전부 ROS 2 기반, `marc_sdk`(Python)로 감싸서 사용 권장. `marc_sdk`는 pip 패키지가 아니라 스타터킷 루트의 소스 폴더(경로만 PYTHONPATH에 잡으면 바로 import).

## 2. 베이스라인 코드 구조

- `participant_app.py` — SDK 연동 골격(진입점). **건드리지 않고 그대로 사용**. 실제로 열어보니 Stage 2 흐름(스탠드오프 접근 → 직진 최종 접근 → pick → 배달, 전복 방지용 팔 접기 등)이 꽤 정교하게 구현돼 있어 참고 가치가 큼 (§9-5).
- `mock_agent_vla.py` — **교체 대상** (Stage 1/2 인식). 실제로는 `mock_demo_data.yaml`에서 `voice_command` 텍스트를 키로 정답을 찾아 반환하는 가짜 구현.
- `mock_agent_navigation.py` — 교체·개선 대상이지만, 안의 `OccupancyGridPlanner`(A*)·`GoalSeekController`·`PathFollower`는 완성도 높은 재사용 가능 코드 (§9-5). Stage 1만 할 땐 손댈 필요 없음.
- `mock_agent_manipulation.py` — 참조용 폴백(고정 keyframe, placo 불필요), 현재 실행 경로 아님. 실제 실행 경로는 `arm_pick.py`(placo 클로즈드루프).
- `arm_pick.py`, `arm_kin.py` — 참조 코드, **그대로 사용 가능** (집기 위치·자세만 실제 인식으로 넘겨주면 부분점수 획득 가능).
- `mock_demo_data.yaml` — 데모 시나리오에서 추출한 데모 전용 정답 데이터(실제 대회엔 없음, mock 에이전트가 참조하는 값). **§5의 실측 클래스명 근거이기도 함.**

개발 흐름: `demo/`를 개발 환경으로 복사 → mock을 실제 구현으로 교체 → 호스트에서 `launch.sh`로 반복 확인 → 어느 정도 되면 `docker compose up`으로 도커 동작 검증(심사와 동일 방식) → 제출.

## 3. SDK 제공 함수 vs 우리가 구현할 부분

**SDK가 제공(그대로 호출만 하면 됨):**
- 콜백: `@client.on_mission`, `@client.on_stage2_mission`, `@client.on_score` 등
- 센서 조회: `get_cctv_image()`, `get_cctv_info()`, `get_cctv_ground_height()`, `list_cctv()`, `get_lidar()`, `get_occupancy_map()`, `is_grasping()`, `is_basket_occupied()`, `get_world_pose()` 등
- 로봇 제어: `send_cmd_vel()`, `send_arm_command()`, `stop()`
- 제출: `submit_grounding()`, `submit_stage2_grounding()`, `task_complete()`

**우리가 직접 구현:**
- `mock_agent_vla.py`의 `process()` (Stage1), `process_stage2()` (Stage2) 내부 로직
- (Stage 2까지 할 경우) `mock_agent_navigation.py`의 경로 계획 로직 — 단, A* 플래너 자체는 이미 있으니 "그대로 쓸지 개선할지"의 문제 (§9-5)

## 4. Stage 1 상세

### 처리 순서 (명령 해석이 먼저, 탐지가 나중)
```
MISSION_COMMAND 수신 (voice_command, round, total_rounds, time_limit)
    ↓
① 자연어 명령 해석 먼저
    → target_type (뭘 찾을지)
    → landmark (기준 사물, 있는 경우)
    → relation (공간관계, 있는 경우)
    → situation (사람 문제인 경우)
    ↓
② 해석 결과 바탕으로 CCTV 영상들에서 실제 탐지
    → list_cctv()로 카메라 목록 확보
    → 각 후보 카메라 get_cctv_image()로 영상 확보
    → target/landmark 함께 보이는 카메라 확정 (camera_id)
    → 픽셀 → world 좌표 변환
    ↓
③ GroundingResult 구성 → submit_grounding() 제출
```

### 명령 구조 2가지 유형 (추정 — 정확한 예문은 문서에 없음, 플랫폼 실행해서 확인 필요)
1. **분실물/관계형 문제**: "OO 옆/근처의 XX" 형태 → target_type + landmark + relation
2. **사람/SAR 문제**: 사람 상황 판단 → target_type="person" + situation

### relation 값 8종
```
near(근처), beside(옆), behind(뒤), front(앞), left(왼쪽), right(오른쪽), on(위-접촉), above(위-공중)
```

### situation 값 4종
```
accident, emergency, abnormal, normal
```
- **v3 확인**: 4종은 문서 명세대로지만, `mock_demo_data.yaml` 실측 예시를 보면 **같은 사람 자세라도 문맥(주변 랜드마크·묘사)에 따라 다른 situation으로 매핑됨** (예: "쓰레기통 위에 앉음"→accident, "쓰러짐/collapsed"→emergency, "벤치에 엎드림"→abnormal, "테이블 위에 누움"→normal). 자세→situation 고정 매핑은 불가능하고 문맥까지 봐야 함.

### GroundingResult 필드 — 전송 payload 형태 (JSON, 실제로는 `marc_sdk.GroundingResult.to_payload()`가 자동 생성)
```json
{
  "camera_id": "...",
  "interpretation": {
    "target_type": "...",
    "landmark": "...",
    "relation": "...",
    "situation": "..."
  },
  "grounding": {
    "anchor_coord": [x, y, z],
    "target_coord": [x, y, z]
  }
}
```

**v3 정정 — 파이썬 dataclass 실제 구조는 다름**: `marc_sdk.types.GroundingResult`는 `target_type`이 **최상위 필드**다 (`interpretation` 중첩은 `to_payload()`가 전송 시에만 만드는 포장).
```python
GroundingResult(
    camera_id="rig_1_a",
    target_type="mug",          # 최상위 필드 (nested 아님)
    anchor_coord=[x, y, z],
    target_coord=[x, y, z],
    landmark="picnic_table",    # 기본값 ""
    relation="on",              # Optional, 사람 문제는 None
    situation=None,             # Optional, 사람 문제일 때만 값
)
```
`real_agent_vla.py`를 다시 만들 때 이 필드명 그대로 채우면 됨.

### 좌표 변환 참고
- CCTV extrinsic: `/tf_static` (world → camera_id), optical 규약(+Z 전방, +Y 아래)
- CCTV intrinsic: `get_cctv_info(camera_id)` (K 행렬)
- 지면 높이: `get_cctv_ground_height(camera_id)` — 픽셀→world 역투영 시 `z = ground_height` 평면 가정 (카메라마다 다름, 도로·잔디 단차 약 10cm 있으므로 배경 전체를 하나의 평면으로 가정하면 안 됨)

### 채점 기준 (Stage 1)
- 카메라 선택 정확도
- 객체·상황 해석 정확도
- 랜드마크·공간관계 정확도
- anchor/target 좌표 정확도 (부분점수)
- 라운드별 평균 = Stage 1 점수
- **정정 이력(2026.R02)**: 기준 랜드마크 정답 좌표를 "문항이 지정한 카메라 안"에서 찾도록 수정됨(과거엔 동일 이름 랜드마크가 다른 카메라에도 있으면 엉뚱한 좌표가 정답으로 잡히는 버그 있었음) → 최신 스타터킷으로 `git pull` 권장.

### 6-1. problems.yaml / problems.yaml.example의 정확한 성격 (신규)

`problems.yaml`(루트)과 `simulation-platform/problems.yaml.example`은 **완전히 동일한 내용**이며, **"문제 예제"가 아니라 "어떤 문제를 낼지 고르는 선택 체크리스트"**다. `id` + `enabled: true/false`만 있고, 실제 `voice_command` 원문·`target_type`·`situation` 같은 문제 본문은 이 파일에 없다.

`marc.sh` 주석에 명시([simulation-platform/marc.sh:76-77](simulation-platform/marc.sh#L76-L77)): "no scenario file is shipped in this repo" — 실제 시나리오(문제 원문)는 도커 콘텐츠 이미지 안에만 있음. `bash simulation-platform/marc.sh select marc2026_chungmu`로 컨테이너 안 TUI를 띄워야 문제 제목/설명을 볼 수 있고, 그 선택 결과가 이 id 목록으로 저장되는 구조.

다만 **id 이름 자체가 문제 내용의 강한 힌트**:
- `lf*` (lost & found, 11개): 분실물 찾기
- `hf*` (harder 분실물류, 8개): lf와 유사하지만 명명 순서가 반대
- `sar*` (search & rescue, 8개): 사람 상태 판단
- `sarH*` (harder SAR, 6개): 더 복잡한 문맥 조합
- `rt*` (stage2 retrieval, 6개): 회수 배달 문제

## 7. 라이다가 필요한 이유 (Stage 2용, Stage 1만 할 땐 필수 아님)

- CCTV(환경 카메라)는 Stage 1의 "인식" 용도
- 라이다는 로봇 몸체에 탑재된 센서(Velodyne VLP-16, `PointCloud2`)로, Stage 2에서 실제 주행 시 근접 장애물 회피용
- 점유지도(`get_occupancy_map()`)는 정적 도로 정보만 담음(사람·물체 없음) → 실시간 장애물 감지는 라이다 담당
- 장애물이 정적이므로(사람 이동 없음) 표준 ROS2 navigation(전역계획+라이다 지역회피)으로 충분

## 8. 디텍션 모델 관련

- **대회가 지정한 모델 없음** — 자유 선택
- **런타임 인터넷 완전 차단** — 가중치·의존성은 빌드 시점에 도커 이미지에 baking 필수 (§0-3 공지사항 1번과 일치)
- 탐지 모델은 전체 클래스를 커버해야 함 (라운드마다 target/landmark가 다름), 런타임에 이번 라운드 무관 객체는 무시 가능

### 2026년 기준 모델 옵션 비교
| 모델 | 특징 |
|---|---|
| YOLO11/YOLOv8 (Ultralytics) | 가장 무난, 학습·배포 쉬움, 문서·커뮤니티 풍부, 단 AGPL-3.0 라이선스 |
| RF-DETR | 2026년 최고 정확도로 꼽힘, COCO 60mAP 최초 돌파, Apache 2.0 |
| Grounding DINO / YOLO-World | 텍스트 프롬프트로 바로 탐지(재학습 불필요), auto-labeling에도 유용, 이 대회처럼 "명령→대상 특정" 구조와 궁합 좋음 |

→ 실전 추천: 처음엔 YOLO11로 빠르게 파이프라인 완성 → 정확도 개선 필요하면 RF-DETR 실험, 또는 Grounding DINO로 auto-labeling해서 YOLO 학습 데이터 보강하는 하이브리드도 고려 가능

## 9. 데이터셋 생성기 → YOLO 학습 파이프라인

### 데이터셋 생성기 (시뮬레이션 플랫폼에서 자동 생성)
```
cd simulation-platform
bash marc.sh dataset-gen
# 또는: docker compose --profile dataset-gen up
```
- 옵션: `ENV_MARC_SCENARIO`, `HEADLESS=true`, `TRAINER_AUTO_SCENES=100` (한 번에 최대 200장면)
- 결과물: `trainer_output/<시나리오>/scene_<번호>/<카메라>.json` + `.png` + `_overlay.png`(라벨 확인용)
- JSON 구조: `detections`(class, bbox[x_min,y_min,x_max,y_max], occlusion) + `image`(width/height, **v3 정정**: 해상도는 `camera`가 아니라 `image` 키에 있음) + `camera`(intrinsic/extrinsic)
- **주의(2026.R03 패치)**: 캔·티슈처럼 눕혀 배치하는 물체, 자전거·킥보드·쓰레기통처럼 넘어뜨려 배치하는 물체의 bbox 좌표가 과거엔 실제보다 위쪽으로 잘못 기록됐었음(사람·벤치·차량 등 고정 대상은 영향 없었음). **패치 이후 이미지를 다시 생성했는지 반드시 확인.**
- **v3 추가 확인**: 재스폰(dataset-gen Shuffle/Switch Camera) 시 물체 위치가 scale만큼 곱해져 카메라 밖/땅 밑으로 튀는 버그가 있었으나, `boot.py`가 실행 시 자동 적용하는 패치(§14)로 이미 수정돼 있음 — 최신 콘텐츠 이미지 사용 시 걱정 불필요.

### JSON → YOLO 포맷 변환 (`demo/train_yolo11.py convert`, 이미 구현/디버깅 완료)
- 2026-08-22 작업기록에서 해상도 조회 버그(`payload["camera"]`만 보고 `payload["image"]`를 안 봐서 0/0 산출)를 수정해 정상 동작 확인(181 train / 20 val images).
- 사람 클래스는 `person` 하나로 뭉개지 않고 `person_*` 7종 그대로 유지(situation 4종 구분을 위해).
- OOM 대응 `--batch`/`--workers` CLI 옵션 추가됨.
- **단, 이 스크립트는 `real_agent_vla.py`에서 `DET_CLASSES`를 import하는 구조라, §5에서 언급한 대로 `real_agent_vla.py`를 먼저 다시 만들어야 실행 가능.**

### YOLO 학습
```python
from ultralytics import YOLO
model = YOLO("yolo11n.pt")
model.train(data="data.yaml", epochs=100, imgsz=1280)  # CCTV 해상도 1280x720 기준
```

### 실제 파이프라인 연결 (재구성 참고 스켈레톤)
```python
# real_agent_vla.py 골격
class RealVLAGrounding:
    def __init__(self, weights_path="weights/best.pt"):
        self.model = YOLO(weights_path)
    def process(self, voice_command, camera_ids=None) -> GroundingResult:
        target_type, landmark, relation = self._parse_command(voice_command)  # 명령 해석 먼저
        for cam_id in camera_ids:
            img = self._to_numpy(client.get_cctv_image(cam_id))
            results = self.model(img)
            det = self._find_target(results, target_type, landmark)
            if det:
                coords = self._pixel_to_world(det, cam_id)
                return GroundingResult(camera_id=cam_id, target_type=target_type,
                    anchor_coord=coords["anchor"], target_coord=coords["target"],
                    landmark=landmark, relation=relation)
        return GroundingResult(camera_id="", target_type=target_type,
                                anchor_coord=[0,0,0], target_coord=[0,0,0])
```

## 9-5. 실제 재구현에 그대로 참고 가능한 베이스라인 코드 (신규 — v3에서 전 파일 확인)

`demo/participant_app.py` + `mock_agent_navigation.py` + `manipulation/`을 실제로 읽어본 결과, Stage 2용 참고 코드가 예상보다 훨씬 완성도가 높음. VLA(인식) 부분만 새로 짜면 Stage 2 나머지는 상당 부분 재사용 가능.

**A\* 경로계획 (`mock_agent_navigation.py`)**
- `OccupancyGridPlanner`: 점유격자 기반 8방향 A*, line-of-sight 경로 단순화, 로봇 반지름만큼 침식(inflation), 씬 안 정적 장애물(차량 등)을 반경으로 깎아내는 기능까지 포함.
- `GoalSeekController`/`PathFollower`: P제어 기반 goal-seek, 큰 헤딩 오차는 제자리 회전 후 전진(Ackermann 조향 한계 고려).
- 그대로 쓰거나, VLA 결과 좌표만 넘겨주는 식으로 재사용 가능.

**로봇 팔 pick (`manipulation/arm_kin.py` + `arm_pick.py`)**
- placo(Pinocchio) 기반 DLS(damped least squares) 클로즈드루프 IK 서보. `pnp_params.json`으로 파라미터(집기 깊이, 운반 높이, 그립 각도 등) 튜닝 가능.
- **grasp 성공 판정**: 힘센서 없이 `inner_finger_knuckle` 조인트 각도로 간접 판정 — 빈손으로 닫으면 ~35°, 물체가 있으면 그보다 덜 닫힘. `is_grasping()`/`is_basket_occupied()`(SDK 제공, True/False/None)와 병행 사용.
- 실패 시 최대 2회 재시도 로직 내장.

**`participant_app.py`의 Stage 2 주행 전략 (그대로 참고 가치 큼)**
- 물체를 향해 바로 돌진하지 않고 **정면 0.58m 스탠드오프까지 A* 주행 → 직진으로 최종 접근** (물체를 깔고 지나가는 것 방지).
- **주행 전 항상 팔을 HOME으로 접음**(`_stow_arm`) — 위가 무거운 로봇이 회전 중 전복되는 것 방지. 성공적으로 집은 뒤에는 유지, 빈손이면 다시 접음.
- `hint_center`(msg 411, 대략 위치)를 우선 목표로 쓰고 안 오면 grounding 결과의 `target_coord`로 폴백.
- 모든 타이밍은 SIM 시간(`client.now_s()`/`client.sleep()`) 기반 — 렌더링이 무거워 real-time factor가 느려져도 타임아웃이 안 깨짐. **참가자 코드도 `time.sleep()` 대신 `client.sleep()`을 써야 함.**

- 예선과 동일 절차, 태그만 `finals`로 변경. 장소·일정은 §0-3 참고.

## 11. 트러블슈팅 자주 나오는 것

| 증상 | 원인/해결 |
|---|---|
| 뷰포트 검정 화면, 첫 실행 시 멈춘 듯 보임 | 정상 — 씬 로딩에 수 분 소요, 강제종료 금지 |
| WSL2에서 카메라 토픽/화면 안 나옴 | WSL2 미지원. 네이티브 Ubuntu 22.04 필요 |
| ROS2 Humble ↔ Isaac Sim Python 충돌 | 셸 분리 (참가자 코드는 Humble/3.10 셸, 플랫폼은 자체 셸) |
| GPU 인식 실패(`Failed to initialize NVML`) | NVIDIA Container Runtime/드라이버 확인, `--gpus all` 지정 확인 |
| 기동 직후 RTX 렌더러 Segfault | 590+ 베타 드라이버가 원인일 확률 높음 → production 580.x로 교체 + 셰이더 캐시 삭제 |
| `unknown or invalid runtime name: nvidia` | `sudo nvidia-ctk runtime configure --runtime=docker` 후 재시작 |
| DDS 통신 안 됨 | 동일 `ROS_DOMAIN_ID`·동일 LAN 확인, RMW는 Fast DDS 기본값 유지(Cyclone DDS 등으로 바꾸면 안 됨) |
| `marc-base:...: pull access denied` | base 이미지는 로컬 빌드 대상 — `marc.sh setup` 먼저 실행 |
| 성능 느림/VRAM 부족 | 해상도↓, 동시 구독 CCTV 스트림 수↓, 무거운 추론은 별도 하드웨어에서 |
| 라이다 TF 조회 실패 | `boot.py`가 자동 적용하는 `patch_lidar_frameid.py`로 해결됨(§14) — 최신 콘텐츠 이미지면 걱정 불필요 |

## 13. marc_sdk 프로토콜 세부사항 (신규 — client.py/types.py/protocol.py/auth.py 실제 코드 확인)

### 메시지 ID 전체 맵
| ID | 이름 | 방향 |
|---|---|---|
| 100 | SESSION_HELLO | 참가자→플랫폼 (핸드셰이크 1단계) |
| 101 | SESSION_PROOF | 참가자→플랫폼 (핸드셰이크 3단계, HMAC proof) |
| 201 | MISSION_COMMAND | 플랫폼→전체 (Stage1 announce) |
| 202 | COMPETITION_STATE | 플랫폼→전체 |
| 203 | TIME_REMAINING | 플랫폼→전체 |

### 핸드셰이크 (auth.py)
- 토큰은 **절대 네트워크로 전송되지 않음**. `proof = HMAC-SHA256(token, "server_nonce|client_nonce|team_id")`만 전송.
- 실제 세션은 만료되는 `session_key`(SESSION_ACK가 발급)로 관리, 이후 요청엔 이 키만 실림.

### QoS 프로파일 3종 (protocol.py)
- `RELIABLE`/`VOLATILE`: 연산 메시지(JSON), cmd_vel, joint_command, TF/Clock
- `RELIABLE`/`TRANSIENT_LOCAL`: `{team}/response`, occupancy map — late-joiner도 마지막 값 수신 보장
- `BEST_EFFORT`/`VOLATILE`/depth=1: CCTV 등 센서 이미지 — 최신 프레임만

### CCTV 자동 탐색 (client.py)
- 2초 주기 타이머로 `/marc/env/cctv/*` 토픽을 스캔해서 새 카메라를 자동 구독. `list_cctv()`가 그 결과를 반환.
- 참가자가 직접 카메라 목록을 하드코딩할 필요 없음.

### SIM 시간 (`now_s()` / `sleep()`)
- `/clock` 토픽 기반이라 real-time factor가 1보다 느려도(무거운 렌더링, GUI, 부하 큰 채점 하드웨어) 타임아웃/대기 로직이 안 깨짐.
- 참가자 코드도 네비게이션 타임아웃, 정지 감지, 팔 keyframe hold 등 모든 타이밍에 `time.sleep()` 대신 `client.sleep()`을 써야 함(§9-5).

### 센서 피드백의 성격
- `is_grasping()` / `is_basket_occupied()`는 **정답을 알려주는 게 아니라** "센서처럼" 현재 잡았는지/바구니에 뭔가 있는지만 알려줌(True/False/None). 점수·정답 유출 없음.
- `get_cctv_ground_height(camera_id)`도 카메라별로 다른 latched 값 — 카메라 discover 즉시 사용 가능.

## 14. 빌드 체인 및 자동 적용되는 에셋 버그 패치 (신규 — simulation-platform 전체 확인)

### 2단계 이미지 빌드 구조
1. **`Dockerfile.base`**: NVIDIA `isaac-sim:5.1.0`(참가자가 nvcr.io에서 직접 pull, EULA 승낙=본인이 라이선시) + ROS2 humble bridge. `marc-base:ros2-isaacsim-5.1`로 로컬 빌드.
2. **`Dockerfile.practice`**: base 위에 GHCR 공개 콘텐츠 이미지(`ghcr.io/marc-challenge/marc-platform-content:2026.R03`)에서 `COPY --from`으로 시나리오/에셋만 가져옴. **IsaacSim 자체는 재배포하지 않음**(라이선스 제약, NOTICES.md §0-3 참고). `marc-platform:practice`로 로컬 빌드.
- 이 통합 이미지 하나로 platform/dataset-gen/manip-trainer 세 가지 도구를 compose profile로 전환.

### `boot.py` — 부팅 시 자동 적용되는 패치 3종 (idempotent, 실패해도 부팅은 계속됨)
- `patch_lidar_frameid.py`: 라이다 frameId가 TF에 없는 이름(`Velodyne_VLS_128`)이라 TF 조회 실패하던 것을 실제 프레임명(`Base_LiDAR`)으로 수정.
- `patch_object_xformops.py` + `patch_object_rotation.py`: **재스폰(dataset-gen Shuffle/Switch Camera, manip-trainer 재시작) 시 물체 위치가 scale만큼 곱해져 카메라 밖/땅 밑으로 튀던 버그** — xformOp 순서를 `[translate, orient, scale]`로 강제 재정렬. §9의 R03 bbox 버그와는 별개 이슈지만 같은 "재스폰 시 좌표 어긋남" 계열.
- 콘텐츠 이미지가 이미 고쳐진 버전을 배포하면 자동으로 no-op됨(마커/앵커 매칭 방식).

### `marc.sh select`의 동작 원리
- 실제 시나리오가 이 레포에 없어서, `marc-platform:practice` 이미지 안에서 TUI(`select_problems.py`)를 실행해 콘텐츠 이미지 내부의 시나리오를 직접 읽음 → 결과만 호스트 `problems.yaml`로 저장(§6-1).
