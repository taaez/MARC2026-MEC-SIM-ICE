`real_agent_vla.py` 재구현 시 `DET_CLASSES`/`TARGET_CLASSES`/`LANDMARK_CLASSES`/`POSE_CLASSES`/
`RELATION_WORDS`/`SITUATION_WORDS` 정의에 바로 쓸 수 있도록 정리. 출처: `demo/mock_demo_data.yaml`
실측 + `problems.yaml`(id 이름) + `MARC2026_요약_v3.md` §4 + 실제 dataset-gen 산출물 1개 씬(`scene_id: 1`,
`rig_1_a`) 실측(v2) + **dataset-gen "New Scene" 오브젝트 선택 패널 전체 목록(Objects/Landmarks
체크리스트) 대조(v3, 아래 "v3" 표시 항목)**.

> **v3 업데이트**: 씬 하나로 추론하던 것보다 훨씬 신뢰도 높은 근거(오브젝트 선택 패널 = 사실상 전체
> 에셋 목록)가 나와서, **타겟 물체 10종·랜드마크 15종은 이제 거의 확정**으로 봐도 됨(패널과 정확히
> 일치, `juice` 1종만 씬 샘플에서 누락됐던 게 추가됨). `parking`/`park`/`bikerack`이 패널에도 선택
> 항목으로 없는 것도 재확인 — 물체가 아니라 장소 개념이라는 추정이 더 굳어짐. **사람 자세 9종도 패널이
> 말하는 숫자와 일치** — 다만 캐릭터(남/여 학생, 교수 등)별로 자세 클래스명이 정말 똑같이 나오는지는
> 아직 캐릭터 1종(male_student)만으로 확인된 상태라 완전 확정은 아님. 학습 직전엔 그래도 씬을 여러 개
> 생성해서 `detections[].class`를 한 번 더 전수 대조하는 걸 권장.

## 4. situation (제출값, 4종) — 문맥에 따라 결정, 자세와 1:1 아님

| 값 | 의미 |
|---|---|
| `accident` | 사고 |
| `emergency` | 응급 |
| `abnormal` | 비정상 상황 |
| `normal` | 정상 |

### 자세 → situation 실측 매핑 예시 (`mock_demo_data.yaml`에서 확인, 문맥 의존적임에 유의)

| 상황 묘사 | situation | 비고 |
|---|---|---|
| 쓰레기통 위에 앉음 | `accident` | |
| 자판기 위에 앉음 | `emergency` (다른 문항은 `accident`) | 같은 자세, 문항마다 다름 |
| 벤치에 엎드려 누움 | `abnormal` | |
| 테이블 위에 누움 | `normal` | 단순히 누워 쉬는 맥락 |
| 쓰러짐/collapsed | `emergency` | |
| 엎드려 움직임 없음(motionless) | `accident` | "motionless" 등 부가 묘사가 심각도를 올림 |
| 넘어진 자전거 옆 쓰러짐 | `emergency` / `accident` (문항마다 다름) | |
| 구부린 채 움직임 없음 | `emergency` | |
| 자판기 위로 기어올라감(비정상 행동) | `abnormal` | "climbed" 같은 표현 |
| 여러 사람 중 가장 위급한 사람 특정 | 그 사람 상태에 따름 | `sarH6_most_critical` — 비교/우선순위 판단 필요 |

**결론**: 자세 클래스만으로 situation을 고정 매핑할 수 없고, 명령 문장의 부가 묘사("motionless", "collapsed", "climbed", "needs help" 등)까지 같이 파싱해야 함. 이게 자연어 명령 해석(§4 처리순서 ①)이 탐지보다 먼저 와야 하는 이유.

## 7. 오프라인 라벨(dataset-gen JSON)과 런타임 API의 카메라 파라미터 형식이 다름 (v2 신규)

실측 씬 JSON의 `camera` 필드는 `position`/`orientation_euler_deg`/`focal_length_mm`/`horizontal_aperture_mm`/
`vertical_aperture_mm`/`ground_height` 같은 **물리 카메라 파라미터(USD 스타일)**로 돼 있음. 반면 실제
대회 런타임에서 참가자가 받는 건 `client.get_cctv_info(camera_id)`가 주는 `sensor_msgs/CameraInfo`
(K 행렬 기반 intrinsic)와 `/tf_static`(extrinsic)입니다. **둘은 형식이 다르므로**:
- 학습 데이터 라벨 변환(`train_yolo11.py convert`)에는 이 JSON 그대로 써도 무방
- 하지만 `real_agent_vla.py`의 `_pixel_to_world`(실제 추론 시 픽셀→world 좌표 변환)는 **런타임 API
  기준(K 행렬 + tf)으로 별도 구현**해야 함 — 오프라인 JSON의 focal_length_mm 공식을 그대로 재활용하면 안 됨

## 8. 소형 객체 대응 방향 (v2 신규 — 실측 근거 기반 정정)

- **P2 탐지 헤드 추가는 필요**: `pencilcase`(4×3px) 등은 YOLO 기본 구조(P3 stride 8)의 feature map에서
  한 칸도 못 채워서 애초에 구분이 불가능함. P2(stride 4)로 feature 해상도를 올리는 게 직접적인 해법.
- **SAHI는 우리 상황에 원래 목적이 안 맞을 수 있음**: SAHI는 "원본이 모델 입력보다 훨씬 커서 리사이즈
  손실이 큰 경우"를 위한 기법인데, CCTV 원본이 이미 1280×720이고 학습 `imgsz`도 1280으로 맞춰놔서
  애초에 리사이즈 손실이 거의 없음 — SAHI가 막아주려는 손실 자체가 우리 파이프라인엔 없음. P2를 먼저
  시도하고, 그래도 부족하면 SAHI를 "손실 방지"가 아니라 "디지털 줌"(타일을 확대해서 넣기) 용도로
  재해석해서 실험해보는 순서가 합리적.
