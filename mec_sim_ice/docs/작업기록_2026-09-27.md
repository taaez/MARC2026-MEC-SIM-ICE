# 작업기록 2026-09-27

umbrella·tumbler·pencilcase에 걸어둔 클래스별 검출 문턱(0.20)이 **실제로는 한 번도 적용되지
않고 있던 문제**를 찾아 `yolo_adapter.py`에서 고쳤다. 로컬 conda 환경(`MARC2026`)을 새로 구성해
실제 가중치·저장된 기록으로 수정 전후를 비교했다. 기록이 있는 범위에서는 점수 변화가 없었다.
로컬 작업 트리만 수정했고 commit·push는 하지 않았다.

## 1. 문제 — 클래스별 문턱 0.20이 두 경로 모두에서 무시됨

`yolo_adapter.py`는 작은 target 3종의 문턱을 낮춰 두었다.

```python
SMALL_TARGET_MIN_CONF = {"tumbler": 0.20, "pencilcase": 0.20, "umbrella": 0.20}
```

근거는 2026-08-29 실측이다. umbrella가 정답 카메라에서 0.249로 나와 문턱 0.25에 걸린 lf08은
25점, 거의 같은 장면에서 0.254로 통과한 hf08·rt02는 94점대였다. 그런데 이 0.20은 어느 경로에서도
박스에 닿지 못하고 있었다.

**모델 B 단독 경로** (`infer_cameras` → `detections_from_result`)

- `infer_cameras`가 `model(img, imgsz=imgsz, verbose=False)`로 **conf를 넘기지 않고** YOLO를 불렀다.
- 제출본이 고정한 `ultralytics==8.3.170`의 `Model.predict`는 conf를 안 넘기면 0.25를 쓴다.
  ```python
  custom = {"conf": 0.25, "batch": 1, "save": is_cli, "mode": "predict", "rect": True}
  args = {**self.overrides, **custom, **kwargs}
  ```
- 그래서 0.20~0.25 박스는 YOLO 안에서 먼저 잘렸고, 0.20을 검사하는 `detections_from_result`에는
  0.25 이상 박스만 도착했다.
- `vla_grounding_agent.py` 주석의 "문턱 0.10/0.15/0.25는 결과가 완전히 동일했다"는 관찰도 같은
  원인으로 설명된다. 0.25 아래는 YOLO가 먼저 잘랐으니 결과가 같을 수밖에 없었다.

**라이브 경로** (모델 B + 소형 모델 라우팅, `RoutedDetector`)

- `load_detector`가 `RoutedDetector(conf=0.25)`로 모델 B의 컷을 0.25에 고정했다.
- 결과를 바꾸는 `detections_from_routed`에는 클래스별 문턱 검사가 아예 없었다.

**영향**

- umbrella·tumbler·pencilcase는 모두 모델 B 담당 클래스다. 소형 모델(sunblock·tissue·disposable_cup)과
  담당을 나눈 것과는 관계없이 발생한다.
- lf08 명령("Find the umbrella dropped in the empty parking space.")은 "on" 관계가 아니라서
  `on_target_probe_augment`의 재탐색(conf 0.001)도 동작하지 않는다. DINO도 꺼져 있다. 즉 0.25 아래로
  나오면 구제 경로가 없다.

## 2. 수정 내용

### 파일별

| 파일 | 변경 |
|---|---|
| `vla_grounding/yolo_adapter.py` | 아래 5곳 |
| `vla_grounding/test_yolo_adapter.py` | `check_class_thresholds()` 테스트 추가 |

**`yolo_adapter.py`**

1. `_yolo_conf_floor(min_conf, min_conf_by_class)` 추가 — 기본 문턱과 클래스별 문턱 중 가장 낮은 값(현재 0.20)을 돌려준다. YOLO 내부 컷으로 넘길 값이다.
2. `infer_cameras` (B 단독 경로) — YOLO를 부를 때 `conf=_yolo_conf_floor(...)`를 넘긴다. 이후 `detections_from_result`가 클래스별로 다시 거르는 건 기존 그대로다.
3. `load_detector` (라우팅) — `RoutedDetector`의 모델 B 컷을 `_yolo_conf_floor(conf, SMALL_TARGET_MIN_CONF)`로 내린다.
4. `detections_from_routed` — `min_conf`, `min_conf_by_class` 인자를 받아 **모델 B 담당 클래스에만** 클래스별 문턱을 적용한다. 소형 모델 담당 클래스(`model.owned`)는 서브모델 문턱을 이미 통과했으므로 다시 거르지 않는다(점수 척도가 달라서). `infer_cameras`가 이 인자를 넘긴다.
5. `predict_result` (기록용 에이전트 `record_agent_vla.py` 전용) — 3번 때문에 모델 B 컷이 내려갔으므로, 라우팅 경로에서도 모델 B 담당 클래스를 `conf`로 다시 자른다. 기록용 경로의 동작은 바뀌지 않는다.

`training/small_object_detection/predict.py`는 평가 스크립트(`evaluate.py`)도 같이 쓰므로 건드리지 않았다.

### 동작 변화

| 대상 | 수정 전 | 수정 후 |
|---|---|---|
| umbrella·tumbler·pencilcase (라이브) | 0.25 미만 버림 | **0.20 이상 통과** |
| 나머지 모델 B 담당 28종 (라이브) | 0.25 이상 | 0.25 이상 (변화 없음) |
| 소형 모델 담당 3종 | small_conf 0.25 | small_conf 0.25 (변화 없음) |
| 기록용 에이전트 (`record_agent_vla.py`, conf 0.35) | 0.35 이상 | 0.35 이상 (변화 없음) |
| `offline_score.py`·`run_offline.py`에 `--conf`를 0.25 **미만**으로 준 경우 | YOLO가 0.25에서 잘라 무시됨 | 그 값이 실제로 적용됨 |

**나머지 클래스가 바뀌지 않는 이유**: YOLO의 NMS는 클래스별로 점수 높은 박스부터 남긴다. 점수가 더
낮은 박스를 후보에 추가해도 더 높은 박스를 지울 수 없으므로, 0.25 이상 박스 집합은 그대로다. 늘어난
0.20~0.25 박스는 뒤에서 클래스별 문턱으로 다시 걸러진다. 이건 NMS 동작에서 나온 추론이고, 실제
가중치로 전후를 비교해 확인한 건 아니다.

### 3.2 오프라인 채점 전후 비교

위 두 라운드만 담은 기록 폴더로 `offline_score.py --no-stage2-exec`를 수정 전·후 코드에서 각각 돌리고

- **25문항 모두 점수 동일** (better 0 / worse 0).
- hf07(오탐이 정답 카메라에 생긴 문항)은 수정 전후 모두 35.00점, 원인도 "랜드마크_오답"으로 같다. 원래부터 기준물을 잘못 잡던 문항이라 추가된 오탐이 결과를 바꾸지 않았다.

**확인하지 못한 것**

- lf08(umbrella 0.249로 25점이던 문항)이 수정으로 살아나는지는 재현하지 못했다. 로컬 `records/`에 lf08 라운드가 없고, 채점기가 빌려 쓴 프레임에서는 umbrella가 원래 0.25를 넘어 수정 전에도 93.97점이었다.

- **DINO는 쓰지 않는다** (팀 결정). GPU 여유가 부족하고, 로컬 채점기 테스트에서 랜드마크-타겟 관계를 제대로 이해하지 못했으며, 공개 가중치 품질도 낮다.
