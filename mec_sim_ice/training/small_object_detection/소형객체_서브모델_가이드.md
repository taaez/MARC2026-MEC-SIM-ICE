# 소형 객체 서브모델 가이드

`sunblock` / `tissue` / `disposable_cup` 3개 클래스만 담당하는 **별도 탐지 모델**을 만들고,
배포 모델 B와 합쳐서 쓰는 방법. 이 문서만 따라 하면 처음부터 끝까지 실행된다.

> **실행 위치**: Isaac Sim 데스크탑의 `mec_sim_ice/training/small_object_detection/`.
> 데이터셋(`dataset_v2`)과 가중치(`*.pt`)는 그 PC에만 있다 (`.gitignore`가 제외).
> Windows 개발 PC에서는 §1의 자체 점검만 돌아간다.

## 0. 한 눈에

| | |
|---|---|
| **문제** | B가 이 3클래스를 val에서도 절반 이상 놓친다 (R 0.375~0.490) |
| **원인** | 객체가 5~8px인데 stride-8 격자 한 칸이 8px — 객체가 격자 1칸에 통째로 들어감 |
| **해결** | 원본을 겹치는 타일로 잘라 **2~4배 확대해서 본다** + 3클래스 전용 모델로 분리 |

| **건드리지 않는 것** | **B의 가중치·구조·학습 그 무엇도 수정하지 않는다** |

## 1. 왜 필요한가

YOLO11은 n/s/m/l/x 전부 stride `[8, 16, 32]`로 동일하다. 스케일을 올려도 채널 폭과 깊이만
늘 뿐 **격자 해상도는 그대로**다. 가장 세밀한 특징맵(stride 8)조차 격자 한 칸이 모델 입력
기준 8×8px인데, 대상 3클래스는 평균 5~8px이다. **객체 하나가 격자 한 칸보다 작다.**

이 상태에서는 IoU 기반 라벨 할당과 CIoU loss가 근본적으로 불안정하다. 얼마나 불안정한지는
`selftest.py`가 실측으로 확인해 준다:

```
PASS  2px shift on a 6px box FAILS IoU@0.5
PASS  2px shift on a 6px box PASSES center match
```

6px 박스가 **2px 밀리기만 해도** IoU@0.5를 못 넘는다. 눈으로는 명백히 맞는 탐지인데도
학습 신호와 평가 양쪽에서 실패로 처리된다.

### 이미 시도했다가 실패한 것들 (반복 금지)

| 시도 | 결과 |
|---|---|
| 오버샘플링 ×4 (A, C) | 3클래스 ±0.02 노이즈, 다른 클래스 9~21개 하락 |
| GT copy-paste 샘플링 (D, E) | recall↑ precision↓ 상쇄, 타겟 mAP 순손실 |
| P2/stride-4 헤드 추가 | 34클래스 **전부** 스톡보다 낮음 → 폐기 |
| GT 크롭 학습 | yolo11s 단독보다 낮음 |

공통점: **B(공유 모델)를 건드리면 특정 클래스 개선이 다른 클래스 손해로 되돌아온다.**
로그상 이 3클래스를 유의미하게 움직인 것은 `yolo11n → yolo11s` 단 한 번(+0.10~0.15)뿐이고,
그 위에 얹은 데이터 개입은 전부 노이즈 범위였다. 그래서 이번에는 **B를 격리하고 별도 모델을
추가**하는 구조로 간다.

## 2. 기존 모델·논문 대비 무엇이 다른가

이 파이프라인은 새 아키텍처가 아니다. **스톡 YOLO11 + 알려진 기법 3개를 이 프로젝트 조건에
맞게 잘라낸 것**이다. 어디를 따랐고 어디서 벗어났는지가 이 절의 내용이다.

### 2.1 스톡 YOLO11 (Ultralytics 8.4.126) 대비

| 항목 | 스톡 | 여기 | 왜 |
|---|---|---|---|
| 백본/넥/헤드 | 그대로 | **그대로 (무수정)** | P2 헤드 추가는 이미 실패. 구조를 안 건드리는 게 이 프로젝트의 결론 |
| stride | [8,16,32] | **[8,16,32] 동일** | 해상도 천장은 입력 확대로 우회, 구조로 낮추지 않음 |
| loss | CIoU + DFL + BCE | **동일 (1차)** | NWD는 조건부 2차 카드 (§8) |
| 클래스 수 | 80 → 34 (B) | **3** | 용량을 3클래스에만 씀 |
| 입력 | 원본 1280×720 | **640 또는 320 타일을 imgsz 1280으로** | 유일한 실질 변경점 |

**즉 코드 수준의 모델 수정은 0이다.** 바뀐 것은 모델에 무엇을 어떤 배율로 먹이느냐뿐이다.

### 2.2 SAHI (Akyon et al. 2022, *Slicing Aided Hyper Inference*) 대비

| 항목 | 논문 | 여기 | 왜 |
|---|---|---|---|
| 추론 슬라이싱 | ○ | **○ (동일)** | 핵심 아이디어 그대로 |
| 슬라이스 파인튜닝 | 권장 | **○ (필수로 취급)** | 원본 학습 + 타일 추론은 학습/추론 스케일이 어긋남 |
| 전체 이미지 패스 병합 | 기본 ON | **기본 OFF** (`full_pass`) | 서브모델은 확대된 타일만 봤음 → 축소된 전체 프레임은 OOD |
| 타일 간 중복 처리 | NMS/NMM | NMS **+ 내부 경계 배제** | 잘린 사본이 온전한 사본보다 높은 confidence를 받는 경우가 있어, 내부 경계에 붙은 예측은 아예 버림 (논문에 없는 추가) |
| 적용 범위 | 모델 전체 | **3클래스 서브모델만** | 31클래스는 B가 이미 mAP50 0.68~0.94로 잘함. 전체 타일링은 낭비이고 런타임 예산도 못 맞춤 |

**가장 큰 차이는 "배율을 명시적으로 관리한다"는 점**이다. SAHI 구현들은 대개 슬라이스 크기만
받는데, 실제 이득은 `train_imgsz / tile` 배율에서 나온다. 640 타일을 imgsz 640으로 돌리면
**아무 효과가 없다** — 6px는 여전히 6px다. 그래서 여기서는 배율을 `tiling.json`에 기록하고,
학습 시 배율 ≤ 1.0이면 **실행을 거부**한다.

### 2.3 NWD (Wang et al. 2021, *Normalized Gaussian Wasserstein Distance*) 대비

| 항목 | 논문 | 여기 |
|---|---|---|
| 사용 여부 | 핵심 기여 | **1차에서 미사용** |
| 정규화 상수 C | 12.8 (AI-TOD 평균) | 쓰게 되면 **실측 6~8px로 재튜닝** |
| 적용 지점 | loss + 라벨 할당 | (2차) `loss.py` BboxLoss + `tal.py` TaskAlignedAssigner |

**왜 안 쓰는가**: NWD는 "객체가 격자보다 작아 IoU가 무의미하다"는 상황을 loss 쪽에서 푸는
방법이다. 그런데 타일링으로 객체가 12~24px가 되면 **그 상황 자체가 상당 부분 해소된다.**
둘을 동시에 넣으면 어느 쪽이 효과를 냈는지 알 수 없고, Ultralytics 내부 수정은 되돌리기도
어렵다. 그래서 순서를 나눴다 (§8).

참고로 이 프로젝트 객체(5~8px)는 AI-TOD 평균(12.8px)보다도 작다. 논문 기본값 C=12.8을 그대로
쓰면 효과가 없거나 역효과일 수 있다는 뜻이다.

### 2.4 병합 = 클래스 라우팅 (WBF 아님)

| 항목 | 일반적 앙상블 | 여기 |
|---|---|---|
| 방식 | WBF/NMS로 융합 | **클래스 라우팅** (concat) |
| 근거 | — | 두 모델의 담당 클래스가 **겹치지 않음** (B 31, 서브모델 3) |

대회 때 프레임 한 장이 들어오면 B와 서브모델이 **같은 이미지**를 본다. 서브모델은 타일로
쪼개 보지만 결과를 원본 좌표로 되돌리므로, 둘 다 같은 프레임·같은 좌표계에 박스를 찍는다.
클래스도 안 겹친다. → **B에서 3클래스 빼고 + 서브모델 3클래스 붙이고 concat**. 조율할
지표가 필요한 충돌이 없다.

**WBF(`--fuse`)는 옵션으로만 남겨뒀다.** 3클래스 내부에서 B의 예측을 교차검증으로 쓰는
경로인데, 두 가지 이유로 기본이 아니다:

1. 두 모델 confidence 스케일이 다름 → calibration 필요
2. WBF는 합의 안 된 박스 점수를 깎음 — `selftest.py`가 못박아 둠:
   `PASS  lone WBF score is halved with 2 models (0.8 → 0.4)`.
   배포 컷이 conf=0.35 하드 컷이라, 0.6짜리 정답이 0.3으로 깎여 **탈락**할 수 있다.

**남는 실제 충돌은 하나**: 서브모델 FP가 B의 다른 클래스 탐지와 공간적으로 겹치는 경우
(차 조각을 컵으로 오인 등). 근데 B는 객체 전체를, 서브모델 FP는 작은 조각을 잡으므로 IoU가
높게 겹칠 일이 드물다. `evaluate.py`의 5번 리포트가 이게 실제로 얼마나 나는지 보여준다 —
그 숫자를 보고 나서 단방향 veto가 필요한지 판단한다. 지금은 **plain concat이 기본**이다.

### 2.5 요약

- **새로 만든 것**: 없음. 아키텍처도 loss도 스톡.
- **논문에서 가져온 것**: SAHI의 슬라이스 학습/추론.
- **논문에서 뺀 것**: SAHI의 전체 이미지 패스, NWD 전부, WBF 기본 적용.
- **논문에 없는데 넣은 것**: 배율 강제 검증, 내부 타일 경계 예측 배제, 크기 게이팅,
  클래스 라우팅, 서브모델 전용 conf.

빼고 넣은 것들의 근거는 전부 "conf=0.35 컷을 통과해야 점수가 된다"는 이 대회 고유 조건이다.

## 3. 전체 흐름

```
                        [ 원본 1280x720 프레임 ]
                                  |
             +--------------------+--------------------+
             |                                         |
      모델 B (34클래스)                    겹치는 타일 6장 (640px)
      imgsz 1280, conf 0.35                            |
             |                              각 타일을 imgsz 1280으로
             |                              (= 2배 확대) 서브모델 추론
             |                                         |
      3클래스 예측은 버림                    타일 좌표 -> 원본 좌표 변환
      (31클래스만 남김)                      내부 경계 예측 배제
             |                              크기 게이팅 (<= 64px)
             |                              타일 간 NMS
             |                                         |
             +--------------------+--------------------+
                                  |
                      클래스 라우팅으로 concat
                                  |
                     [ 34클래스 최종 탐지 결과 ]
```

학습 시에는 위 오른쪽 가지와 **똑같은 격자**로 잘린 타일로 서브모델을 학습한다. 학습과 추론의
격자가 어긋나면 조용히 성능만 떨어지므로, 격자 계산은 `common.tile_grid()` 한 곳에만 있고
파라미터는 `tiling.json`으로 전달된다.

## 4. 실행 순서

### 4-0. 자체 점검 (가중치·데이터 불필요, 10초)

```bash
cd mec_sim_ice/training/small_object_detection
python3 selftest.py
```

`all checks passed`가 나와야 한다. 타일 격자 커버리지, 좌표 변환, 경계 배제, 크기 게이팅,
NMS/WBF, 매칭/AP 계산까지 33개 항목을 검사한다. 여기서 실패하면 아래 단계는 의미가 없다.

### 4-1. 타일 데이터셋 만들기 (수 분)

```bash
python3 make_tiled_dataset.py \
    --base ../../datasets/dataset_v2 \
    --out ../../datasets/dataset_small_t640 \
    --tile 640 --train-imgsz 1280
```

`dataset_v2`에서 3클래스만 남기고(0,1,2로 재번호) 겹치는 격자로 잘라 새 데이터셋을 만든다.
`data.yaml`과 함께 **`tiling.json`**(타일 크기·겹침·학습 imgsz)이 저장되고, 이후 단계는 전부
이 파일을 읽는다 — 숫자를 다시 타이핑하지 않는다.

출력 마지막에 나오는 이 세 줄이 핵심이다:

```
upscale factor at train imgsz=1280: 2.00x
  box longest side, model px  : p10=... p50=... p90=...
  stride-8 cells across a median box : 1.86
```

마지막 값이 **1.0 이하면 타일링이 아무 일도 안 한 것**이다. §5 참고.

주요 옵션:

| 옵션 | 기본 | 설명 |
|---|---|---|
| `--tile` | 640 | 타일 크기. 320으로 낮추면 배율 4배, 타일 수 2.5배 |
| `--overlap` | 0.25 | 이웃 타일과 겹치는 비율 |
| `--neg-per-pos` | 0.5 | 객체 있는 타일 1장당 빈 타일 몇 장 (원본은 background 0장이라 필요) |
| `--min-vis` | 0.5 | 타일 경계에 잘린 박스를 살릴 최소 면적 비율 |

### 4-2. 서브모델 학습 (GPU, 수 시간)

```bash
python3 train_small.py \
    --data ../../datasets/dataset_small_t640 \
    --weights yolo11s.pt \
    --epochs 200 --name small_t640
```

- imgsz는 `tiling.json`에서 자동으로 읽는다. **배율 ≤ 1.0이면 실행을 거부**한다.
- 전체 로그는 `test/logs/train_<시각>_small_t640.log`에 자동 저장된다.
- OOM으로 batch가 계속 자동 강등되면 `--batch 4 --workers 2`처럼 직접 낮춰라
  (B도 7.7GB에서 16→8→4로 떨어졌다).
- 중단됐으면 `--weights ../../training_results/small_object_detection_runs/detect/small_t640/weights/last.pt --resume`.

> 여기서 나오는 Ultralytics의 val mAP는 **학습 모니터일 뿐이다.** 학습과 같은 타일 분포에서
> 잰 값이라 배포 성능이 아니다. 판단은 다음 단계에서 한다.

### 4-3. 평가 — 이게 판단 기준 (GPU, 수십 분)

```bash
python3 evaluate.py \
    --base ../../datasets/dataset_v2 --split val \
    --general ../../training_results/yolo_main_runs/detect/train_B_yolo11s/weights/best.pt \
    --small   ../../training_results/small_object_detection_runs/detect/small_t640/weights/best.pt \
    --tiling  ../../datasets/dataset_small_t640
```

**원본 1280×720 이미지**에서 B 단독과 B+서브모델을 한 번의 추론으로 둘 다 재고 비교한다.
출력 5개:

1. `BASELINE` — B 단독 (옛 로그 인용이 아니라 지금 실측한 값)
2. `ROUTED` — B(31) + 서브모델(3)
3. `SMALL CLASSES BY GT SIZE` — **크기 버킷별 recall.** 실패가 원거리 초소형에 몰려 있어서
   전체 평균으로는 안 보인다. `<8px` 칸이 실제 승부처다.
4. `SUB-MODEL CONF SWEEP` — 서브모델 전용 threshold를 정하기 위한 표
5. `SUB-MODEL vs B SPATIAL OVERLAP` — 서브모델 박스가 B 박스와 겹치는 비율을 TP/FP로 분해.
   라우팅은 B가 같은 자리에 뭘 봤든 서브모델 박스를 다 남기므로, 그게 손해인지 여기서 확인한다.
   **FP가 confident한 B 박스 위에 많이 겹치면** → 단방향 veto가 싸게 걸러줌.
   **TP가 많이 겹치면**(picnic_table bbox 안의 컵 등) → veto는 정상 탐지를 죽임, concat 유지.
   지금은 concat이 기본이고 이 표는 "veto가 필요한가"를 데이터로 판단하기 위한 것이다.

유용한 옵션:

```bash
--match center --center-px 8    # IoU 대신 중심거리 매칭 (§1의 이유)
--conf 0.35                     # 배포 컷. 기본값이 이미 0.35
--small-conf 0.25               # 서브모델 컷. 스윕 결과 보고 정할 것
--limit 50                      # 빠른 확인용
```

### 4-4. 배포용 추론

```bash
python3 predict.py \
    --images <이미지 폴더> \
    --general ../../training_results/yolo_main_runs/detect/train_B_yolo11s/weights/best.pt \
    --small   ../../training_results/small_object_detection_runs/detect/small_t640/weights/best.pt \
    --tiling  ../../datasets/dataset_small_t640 \
    --small-conf 0.25 --out preds.json
```

파이프라인에 붙일 때는 `RoutedDetector`를 직접 import 하면 된다:

```python
from predict import TiledPredictor, RoutedDetector

small = TiledPredictor("small_best.pt", "../../datasets/dataset_small_t640", conf=0.25)
det   = RoutedDetector("B_best.pt", small, conf=0.35)
boxes, scores, classes = det.predict(bgr_image)   # classes는 DET_CLASSES 인덱스
```

출력 클래스 id는 34클래스 `DET_CLASSES` 기준이라, 받는 쪽은 모델이 두 개라는 걸 알 필요가 없다.

## 5. 파라미터 고르기 — 배율이 전부다

```
모델이 실제로 보는 객체 크기 = 원본 px × (train_imgsz / tile)
```

| 타일 | @imgsz 1280 | 6px 객체가 | stride-8 격자 | 이미지당 타일 | 학습 비용 |
|---|---|---|---|---|---|
| 640 | 2.0배 | 12px | 1.9칸 | 6 | 기준 |
| 320 | 4.0배 | 24px | 3.7칸 | 15 | 약 2.5배 |
| 640 @ imgsz 640 | **1.0배** | **6px** | **0.75칸** | 6 | **무의미** |

**640(2배)부터 시작하고, 부족하면 320(4배)로 간다.** 4배가 IoU가 안정되는 지점이지만 학습
시간이 2.5배라, 2배로 충분한지 먼저 확인하는 쪽이 싸다. 판단은 4-3의 `<8px` 버킷 recall로.

## 6. 결과 읽는 법

- **31클래스는 두 표에서 완전히 같아야 한다.** B 출력을 그대로 통과시키므로 원리적으로
  달라질 수 없다. 다르면 모델이 아니라 **라우팅 코드가 틀린 것**이다 (evaluate가 이 문구를
  마지막에 출력한다).
- **`SMALL CLASSES BY GT SIZE`의 `<8px` 칸이 진짜 지표다.** 전체 recall은 큰 인스턴스에
  희석된다.
- **conf 스윕에서 F1 최대점을 그대로 쓰지 마라.** 이 과제는 놓치면 0점이라 recall이 precision
  보다 비싸다. FP가 감당 가능한 선에서 recall 쪽으로 치우친 값을 고르는 게 맞다.
- 참고로 B 단독 현재 성적:

| 클래스 | R | mAP50 | mAP50-95 |
|---|---|---|---|
| disposable_cup | 0.490 | 0.575 | 0.237 |
| sunblock | 0.375 | 0.454 | 0.238 |
| tissue | 0.404 | 0.519 | 0.216 |
| (모델 평균) | 0.788 | 0.848 | 0.692 |

## 7. 문제 해결

| 증상 | 원인 / 조치 |
|---|---|
| `no tiling.json at ...` | `make_tiled_dataset.py`를 먼저 실행. 추론 슬라이싱은 학습 슬라이싱과 같아야 하므로 손으로 숫자를 넘기는 경로는 막아 뒀다 |
| `upscale 1.00x buys nothing` | `--tile`을 낮추거나 `--imgsz`를 올려라. 이 상태로는 타일링이 아무 효과가 없다 |
| 학습 중 batch 자동 강등 반복 | `--batch 4 --workers 2`로 직접 지정 |
| 추론이 너무 느림 | `--tile-batch`를 올려라(GPU 메모리 여유 필요). 타일 6장이 B 1장보다 비싸다 |
| 서브모델 FP가 많다 | `--small-conf`를 올리고, `--max-box-px`를 40 근처로 좁혀라 (이 3클래스는 최대 40px) |
| 타일 경계에서 객체를 놓친다 | `--overlap`을 0.35~0.4로 올려라. `--edge-margin 0`으로 배제를 꺼서 원인을 분리해 볼 수도 있다 |
| 31클래스 숫자가 두 표에서 다르다 | 라우팅 버그. 모델 문제가 아니다 |

## 8. 아직 안 한 것

- **NWD (조건부 2차 카드).** 4-3 결과가 부족할 때만 착수. `ultralytics/utils/loss.py`의
  BboxLoss(CIoU 계산부)와 `ultralytics/utils/tal.py`의 TaskAlignedAssigner(IoU alignment
  metric)를 NWD로 교체 또는 블렌딩하고, 정규화 상수 C를 **실측 6~8px 기준으로 재튜닝**한다
  (논문 기본값 12.8 금지). 박스 크기에 따라 CIoU↔NWD를 가중 평균하는 스케일 적응형 블렌딩도
  후보. **Ultralytics 내부를 고치는 작업이라 되돌리기 어려우니, 타일링만으로 얼마나 되는지
  먼저 확정한 뒤에 손댈 것.**
- **실채점 회귀 확인.** `mec_sim_ice/score.py` 39라운드를 라우팅 파이프라인으로 재실행.
- **런타임 예산 측정.** B 1패스 + 타일 6패스가 대회 제한 시간 안에 들어오는지 미측정.
- **행동/문맥 클래스**(예: "쓰레기를 버리는 사람")는 이 작업 범위 밖이다. 단일 프레임
  person crop으로는 원리적으로 구분이 어려워 관계·시간 정보가 필요한 별개 문제다.
