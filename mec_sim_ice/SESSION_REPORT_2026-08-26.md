## 3. 카메라 선택 로직 재설계 (`ae3f187`, `0d7d2b6`)

### 진단 — GT 좌표를 6대 카메라에 투영해 알아낸 것

- **CCTV 6대는 서로 다른 공간을 본다 (시야가 겹치지 않는다).** 39문제 중 38개에서
  정답 target 이 보이는 카메라가 **정확히 1대뿐**이다. 카메라 선택은 순위 매기기가
  아니라 **제약충족** 문제였다.
- **target 클래스만으로는 절대 안 정해진다**: `umbrella` 4개가 4대에, `tumbler` 4개가
  3대에, `trash_can` 3개가 3대에 흩어져 있다.
- 랜드마크가 결정적이다: 18문항은 지목된 랜드마크가 1대에만 있어 즉시 확정되고,
  나머지 21개 중 20개는 "랜드마크와 target 이 가장 가까운 카메라" 로 풀린다
  → **이론상 상한 38/39** (당시 실제는 15/39).
- 오선택 15건 중 7건은 **명령이 명시한 랜드마크가 아예 없는 카메라**를 골랐다.

### 고친 것

1. **카메라 게이트 (순수 폴백 계층)**: 명시 랜드마크 → `area_hint` → 해제.
   좁히지 못하면 이전 동작으로 돌아가므로 **나빠지는 경로가 없다.**
2. **`area_hint` 활용**: 랜드마크를 말하지 않고 구역만 말하는 8문항
   ("in the parking lot")을 구역의 지표 클래스로 좁힌다. `AREA_INDICATOR_CLASSES` =
   `{parking: CAR_CLASSES, park: {picnic_table, bench}}`. "주차 구역 = 차량이 밀집한 곳"
   이라는 **단어의 의미**에서 나온 매핑이라 씬 하드코딩이 아니다. `road` 는 근거
   사례가 없어 일부러 비웠다.
3. **탐지 confidence 를 카메라 간 순위에서 제거**: 서로 다른 장면에서 나온 값이라
   비교 근거가 못 된다. relation 기하 적합도로 고르고 conf 는 동점 처리에만 쓴다.
4. **relation 적합도를 (주, 부) 튜플로 분리**: 근접 계열(on/above/beside/near)은 거리
   임계로만 갈리는 연속값이라 버킷 일치가 근접도 순서를 뒤집으면 안 된다. 방향
   관계는 반대로 일치 여부가 주 신호.
5. **target 미탐지 시 랜드마크만으로 제출** + `target_coord = anchor_coord`.
   빈 제출은 0점 확정이지만 랜드마크만 맞아도 camera/landmark/anchor 배점이 살아있고,
   허용 5m 대비 실측 anchor↔target 거리 중앙값이 1.85m 라 부분점수를 건진다.
6. **사람 문제에도 동일 적용**: landmark 배점은 0점이지만 카메라를 좁혀 주는 단서가
   사실상 랜드마크뿐이라 **camera/anchor/target 65점을 여는 열쇠**다.
7. 사람 문제에서 pose 버킷 때문에 target 을 못 찾으면 제약을 풀어 재탐색.

### 실측이 설계를 두 번 고쳐준 지점

- **기존 테스트 T5 가 첫 구현의 버그를 잡았다.** 관계 적합도를 하나의 점수로 합쳤더니
  "조금 더 먼데 버킷만 맞는" 후보가 더 가까운 후보를 이기는 역전이 생겼다 → 4번으로 수정.
- **area 게이트 첫 버전("차가 있으면 주차장")은 오히려 2문항을 -10점씩 악화시켰다.**
  차량이 6대 중 4대 카메라에 흩어져 검출돼 후보가 안 좁혀졌기 때문이다. "차가
  **밀집한** 곳"으로 바꾸니 8문항 전부 정답 카메라가 유일하게 남았고
  (parking: rig_7_a 4대 vs 나머지 0~1대 / park: rig_1_a 5개 vs 1~2개), 두 문항이
  +69.29 / +10.00 으로 뒤집혔다. **GT 분석만으로는 못 잡았을 문제였다.**
